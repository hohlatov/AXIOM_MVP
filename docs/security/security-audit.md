## Подробный разбор

### 1. CRITICAL — `.env` закоммичен в git, `.gitignore` отсутствует

**Что нашёл.** `git ls-files | grep '^\.env$'` подтверждает: `.env` отслеживается git и фигурирует в истории минимум в 3 коммитах (`476e4dc version 1.0`, `e78368c правки`, `ed47d5e Revert "правки"`). В репозитории вообще нет файла `.gitignore` — соответственно не игнорируются ни `.env`, ни `node_modules`, ни `__pycache__`, ни `.next`.

Проверил (без раскрытия значений): текущий закоммиченный `.env` структурно идентичен `.env.example` — `JWT_SECRET` в нём **до сих пор равен плейсхолдеру** `change-me-to-a-random-64-char-string`, `VK_CLIENT_SECRET` и `SMTP_PASSWORD` пустые. То есть в самом репозитории сейчас не лежит реального прод-секрета — это скорее dev-заготовка, но она **отслеживается git**, а не игнорируется.

**Почему это критично именно для этого проекта.**
`docker-compose.yml` у сервиса `backend` использует `env_file: - .env` — то есть на проде backend буквально запускается с тем `.env`, что лежит в чекауте репозитория на сервере. `docs/audit/03-live-vs-code.md` независимо подтверждает: живой MVP на 100% соответствует этому репозиторию, деплой идёт без скрытых прод-патчей. Если на проде **не был вручную подменён** `JWT_SECRET` на реальное случайное значение (а факт этого аудиту недоступен — конфигурация прод-`.env` не проверялась и заявлена как UNKNOWN в `03-live-vs-code.md`), то `JWT_SECRET` в проде — **общеизвестная строка из публичного `.env.example`**. Алгоритм подписи — `HS256` (симметричный, проверяется тем же секретом). Если это так, любой человек в интернете может сам подписать валидный JWT с произвольным `sub` (UUID любого пользователя) и `type: "access"` — то есть **полный захват любого аккаунта без пароля**, включая аккаунты несовершеннолетних учеников.

Даже если сейчас прод-секрет реальный и случайный — сам факт того, что `.env` отслеживается git без `.gitignore`, означает, что при следующей правке (например, кто-то впишет туда настоящий `SMTP_PASSWORD` или продовый `VK_CLIENT_SECRET` локально и случайно закоммитит) секрет навсегда попадёт в историю git, включая push в любой удалённый репозиторий.

**Риск:** при подтверждении, что прод использует дефолтный `JWT_SECRET`, — критический (полная компрометация аутентификации всех пользователей, включая несовершеннолетних). Даже без подтверждения — сам процесс (нет `.gitignore`, секреты трекаются) уже сегодня создаёт постоянный риск утечки будущих секретов.

**Рекомендация:**
1. Немедленно (до пилота) — вручную проверить на проде реальное значение `JWT_SECRET`, `VK_CLIENT_SECRET`, `SMTP_PASSWORD`. Если совпадают с плейсхолдером/пустые — сгенерировать новые случайные значения (`openssl rand -hex 32` и т.п.) и перевыпустить. Это инвалидирует все выданные JWT — ожидаемо и безопасно для пилота на 100 пользователей.
2. Добавить `.gitignore` с `.env`, `.env.local`, `__pycache__/`, `.next/`, `node_modules/`.
3. `git rm --cached .env` (файл останется на диске, но перестанет отслеживаться) — сделать отдельным коммитом.
4. Оставить только `.env.example`/`.env.local.example` в git.
5. Ротация секретов, если когда-либо в истории git реально лежали боевые значения (по имеющимся данным — не лежали, только плейсхолдеры, но стоит перепроверить всю историю `.env`, не только текущее состояние).

Трудозатраты: 30–60 минут на .gitignore/git rm + ротацию секретов, если потребуется.

### 2. CRITICAL — Postgres и Redis раскрыты наружу, слабые дефолтные учётные данные

**Что нашёл.** `docker-compose.yml`:
```yaml
db:
  image: pgvector/pgvector:pg16
  environment:
    POSTGRES_USER: axiom
    POSTGRES_PASSWORD: axiom
    POSTGRES_DB: axiom
  ports:
    - "5432:5432"
redis:
  image: redis:7-alpine
  ports:
    - "6379:6379"
```
Учётные данные Postgres захардкожены прямо в `docker-compose.yml` (не читаются из `.env`) и представляют собой тривиально угадываемую пару `axiom`/`axiom`. У Redis вообще нет пароля (`requirepass` не задан). Секция `ports:` публикует оба порта на все интерфейсы хост-машины (стандартное поведение Docker для `"host:container"` без явного `127.0.0.1:`), а не только внутри docker-сети между контейнерами (для внутренней связи `ports:` вообще не нужен — достаточно общей docker-сети `depends_on` уже обеспечивает связность).

**Реальный риск для текущего масштаба.** Если хост, на котором развёрнут прод (`axiombackend.relaxdev.ru`), не закрывает 5432/6379 файрволом/security group отдельно от reverse-proxy — это означает: любой в интернете может подключиться напрямую к базе данных с ФИО-подобными персональными данными несовершеннолетних (email, hash пароля, VK ID, история диагностики/чата с ассистентом) через пароль `axiom`/`axiom`, полностью в обход приложения, авторизации и rate limiting. Redis без пароля дополнительно даёт прямой доступ к одноразовым токенам сброса пароля (`pwdreset:*` ключи) — можно перехватывать/генерировать валидные ссылки сброса пароля для любого аккаунта.

Аудит не может подтвердить, действительно ли порты доступны из интернета на текущем хостинге RelaxDev (это требует сетевого сканирования прод-хоста, что выходит за рамки статического аудита и правил "не трогать прод"), поэтому фактическая эксплуатируемость — **UNKNOWN, требует проверки владельцем** (`nmap` с внешней машины по `axiombackend.relaxdev.ru:5432` и `:6379`, либо проверка правил security group/firewall хостинга). Но даже если сейчас случайно закрыто файрволом хостинга, конфигурация в репозитории не даёт для этого никакой гарантии — это не defense-in-depth, а везение.

**Рекомендация:**
1. Убрать секцию `ports:` у `db` и `redis` в prod-конфигурации (или в отдельном `docker-compose.prod.yml`) — оставить их доступными только внутри docker-сети, где к ним обращается `backend`. Если для локальной разработки нужен прямой доступ к Postgres — это остаётся только в dev-конфиге.
2. Заменить `POSTGRES_PASSWORD: axiom` на переменную из `.env` со случайным значением (`POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}`).
3. Задать `requirepass` для Redis (через `command: redis-server --requirepass ${REDIS_PASSWORD}` и обновить `REDIS_URL`).
4. Независимо от изменений в коде — прямо сейчас, до пилота, попросить владельца/RelaxDev подтвердить, что 5432/6379 не достижимы извне на текущем проде.

Трудозатраты: 1–2 часа (правки compose + генерация паролей + ре-деплой), но правка docker-compose.yml — уже не просто документация, это код инфраструктуры, поэтому требует явного одобрения перед внедрением согласно правилам AUDIT MODE.

### 3. HIGH — rate limiting по IP считает адрес реверс-прокси, а не клиента

**Что нашёл.** Это уже задокументированная в коде проблема — `app/core/rate_limit.py` содержит собственный комментарий:

> «За обратным прокси (nginx/Yandex Cloud ALB) `request.client.host` будет адресом прокси, а не реального клиента — на проде нужно либо доверять X-Forwarded-For от известного прокси, либо настроить rate limiting на уровне самого прокси/балансировщика. Сейчас это не настроено — TODO для деплоя.»

Код нигде не читает `X-Forwarded-For`/`X-Real-IP`, доверенных прокси не настроено (`app/core/rate_limit.py`, `rate_limit_by_ip`).

**Реальная критичность для текущего продакшена (за прокси RelaxDev).** Два разных сценария в зависимости от того, как именно устроен прокси:
- Если прокси не пробрасывает реальный IP клиента в `request.client.host` (наиболее вероятный сценарий для простого nginx-проксирования без `proxy_protocol`) — тогда **все** запросы с точки зрения backend приходят «с одного IP» (адреса прокси). Для эндпоинтов с лимитом только по IP (`register`: 5/час, `vk-callback`: 20/час) это означает, что лимит де-факто общий на **всех** пользователей пилота одновременно, а не персональный на атакующего. Пять регистраций в час от любых 5 разных школьников — и регистрация блокируется для всех остальных на час. Это реальный риск **само-DoS** в день открытия пилота, а не только ослабление защиты от атакующего.
- Для `login` и `password-reset/request` есть дополнительный лимит по email (`rate_limit_by_key`), который не зависит от IP — он продолжит работать корректно независимо от того, что происходит с IP. Так что подбор пароля к конкретному аккаунту всё ещё ограничен.

То есть подсистема брутфорс-защиты конкретных аккаунтов не пострадает, а вот доступность регистрации/VK-входа для пилота — реальный риск.

**Рекомендация:** до пилота — либо настроить на прокси RelaxDev проброс `X-Forwarded-For`/`X-Real-IP` и научить `rate_limit_by_ip` доверять только этому заголовку (не доверять ему без прокси, иначе спуфинг), либо, как более простой вариант для MVP, перевести лимиты `register`/`vk-callback` тоже на связку «по IP + по чувствительному идентификатору» (например, по email для `register` — она уже частично уникальна за счёт 409 на дубликат) и явно проверить фактическое поведение на проде до открытия пилота (один тестовый прогон 6+ регистраций подряд с разных реальных устройств/сетей — увидит ли шестое обычное устройство 429).

Трудозатраты: 2–4 часа (настройка доверенного прокси-заголовка + тест на проде).

### 4. MEDIUM — JWT access-токен в `localStorage`

**Что нашёл.** `axiom-frontend/lib/api.ts`: `localStorage.getItem/setItem("axiom_access_token", ...)`; `lib/auth.tsx` кладёт туда access-токен после логина/регистрации/VK. Токен добавляется в `Authorization: Bearer` заголовок на каждый запрос.

**Оценка риска localStorage vs httpOnly cookie.** Классический компромисс:
- `localStorage` уязвим к краже токена через **любой** XSS (в т.ч. через скомпрометированную npm-зависимость, а не обязательно через баг в собственном коде) — скрипт может прочитать токен и отправить его атакующему.
- httpOnly cookie недоступна для JS, но тогда нужна защита от CSRF (SameSite/CSRF-токен), т.к. браузер сам прикладывает cookie к запросам.

Сейчас в коде фронтенда не найдено `dangerouslySetInnerHTML` или иных прямых точек инъекции HTML на пользовательский ввод (в React экранирование по умолчанию), явных XSS-уязвимостей аудит не обнаружил. Но архитектурно `localStorage` — более широкая поверхность атаки, особенно с учётом того, что AI-ассистент в будущем будет рендерить текст, сгенерированный внешней LLM (после интеграции с реальным ИИ-сервисом) — если вывод модели когда-либо будет вставляться как `dangerouslySetInnerHTML`/`innerHTML` (например, чтобы рендерить markdown/форматирование от ИИ) — это открывает stored/reflected XSS через сам чат, и тогда localStorage-токен станет реально эксплуатируемым вектором. Сейчас чат — mock, простой текст, риска нет.

Смягчающий фактор: access-токен живёт всего 60 минут, что ограничивает окно эксплуатации по сравнению с бессрочным токеном; также отсутствие cookie-based сессий означает, что CSRF как класс атак для API вообще не применим — это осознанный плюс текущей архитектуры.

**Рекомендация:** для MVP-масштаба (100 пользователей, mock ИИ, React без `dangerouslySetInnerHTML`) считать риск приемлемым, но:
1. Зафиксировать правило: если/когда ассистент начнёт рендерить форматированный (markdown/HTML) ответ ИИ — использовать безопасный markdown-рендерер с санитайзингом (например, `react-markdown` без `rehype-raw`), никогда не `dangerouslySetInnerHTML` с сырым выводом модели.
2. Как более надёжное решение на будущий этап (не MVP, п. `docs/architecture/02-target-architecture.md`) — рассмотреть переход access/refresh на httpOnly+Secure+SameSite=Strict cookies при коммерческом запуске, когда цена внедрения CSRF-защиты оправдана ростом аудитории.

Трудозатраты сейчас: 0 (принять риск, зафиксировать правило для будущего кода ассистента).

### 5. MEDIUM — нет отзыва токенов; refresh-flow не реализован, хотя настройки под него заведены

**Что нашёл.**
- `logout()` во `axiom-frontend/lib/auth.tsx` — это **исключительно** `setAccessToken(null)` + сброс состояния на клиенте. Никакого запроса на backend при логауте нет.
- Backend не хранит список выданных/отозванных токенов (ни в БД, ни в Redis) — JWT полностью stateless. Значит **отозвать** конкретный access-токен до истечения его `exp` невозможно в принципе — ни через logout, ни, например, при компрометации аккаунта («сменить пароль» не инвалидирует уже выданные токены).
- `REFRESH_TOKEN_EXPIRE_DAYS=30` в `.env.example`/`config.py`, `create_refresh_token()` в `app/core/security.py`, и `refresh_token` реально возвращается в `TokenPair` из `/auth/login`, `/auth/register`… то есть нет, из `/auth/register` refresh не возвращается (там `UserOut`, не `TokenPair`) — возвращается из `/auth/login` и `/auth/vk/callback`. Но **эндпоинта `/auth/refresh` не существует** — grep по всему backend не находит ни одного места, где refresh-токен принимался бы на вход и обменивался на новый access-токен. Фронтенд (`lib/auth.tsx`) получает `refresh_token` в ответе логина, но **нигде его не сохраняет и не использует** — переменная просто отбрасывается.

**Итог:** refresh-механизм — это конфигурация и наполовину написанный код (генерация токена есть, эндпоинт погашения — нет), который сейчас ни на что не влияет: он не используется и не создаёт уязвимости сам по себе (токен генерируется, отдаётся клиенту в теле ответа и тут же забывается фронтендом). Но это создаёт **иллюзию сессионного контроля** для того, кто читает конфиг (`REFRESH_TOKEN_EXPIRE_DAYS=30` выглядит как «сессия длится 30 дней с ротацией», а по факту доступ ограничен ровно 60 минутами access-токена, после чего пользователь получает 401 и должен логиниться заново).

Отдельно: раз refresh-токен нигде не сохраняется на фронтенде, он просто теряется — не риск сам по себе, но и не функциональность. Если/когда refresh будет реализован, обязательно нужна возможность его отзыва (хранить в Redis/БД allowlist или denylist по `jti`), иначе 30-дневный refresh-токен, единожды скомпрометированный (например, через XSS, см. п. 4), будет давать доступ на 30 дней без возможности его прервать даже сменой пароля.

**Рекомендация:**
1. Либо удалить генерацию `refresh_token` из ответов, пока не реализован сам эндпоинт обмена (меньше вводящего в заблуждение кода) — либо, что полезнее для UX, реализовать `POST /auth/refresh`, но сразу с поддержкой отзыва (хранить активные `jti` refresh-токенов в Redis с TTL = `REFRESH_TOKEN_EXPIRE_DAYS`, удалять запись при logout/смене пароля).
2. Реализовать реальный logout: эндпоинт `POST /auth/logout`, который добавляет `jti` текущего access-токена (или хотя бы всех refresh-токенов пользователя) в denylist в Redis до истечения `exp` — недорого технически (Redis уже используется для rate limiting и сброса пароля).
3. Как минимум — задокументировать текущее поведение открыто: «logout не инвалидирует токен на сервере, максимум окна доступа — 60 минут» — это не блокер для пилота на 100 доверенных пользователей, но должно быть осознанным решением, а не забытым TODO.

Трудозатраты: реализация полноценного refresh+revoke — 0.5–1 день. Быстрый вариант (просто убрать неиспользуемый refresh_token из ответов + задокументировать) — 15 минут.

### 6. MEDIUM — отсутствуют security-заголовки

**Что нашёл.** `app/main.py` подключает только `CORSMiddleware`, больше никаких middleware/заголовков. Независимо подтверждено на живом проде (`docs/audit/03-live-vs-code.md`, раздел «Security-заголовки»): нет `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, `Referrer-Policy` ни на фронтенде, ни на бэкенде.

**Риск для масштаба 100 пользователей.** Не критично само по себе (отсутствие этих заголовков — не уязвимость напрямую, а отсутствие второго рубежа обороны), но:
- Без `X-Frame-Options`/`frame-ancestors` в CSP страницы логина/регистрации теоретически можно встроить в `<iframe>` на стороннем сайте для clickjacking (кликджекинг чекбокса согласия родителя, например).
- Без CSP нет второго рубежа защиты от XSS — при появлении XSS в React-коде или в сторонней зависимости (см. п. 4) ничто не ограничит, куда может уйти украденный токен.
- Без HSTS — если когда-либо запрос уйдёт по HTTP до редиректа на HTTPS (не проверялось), возможен downgrade/MITM; для домена за Cloudflare-подобным прокси это частично смягчается конфигурацией самого прокси, но в коде приложения гарантии нет.

**Рекомендация:** добавить `SecurityHeadersMiddleware` в FastAPI (10–15 строк, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, базовый `Content-Security-Policy`) и аналогичные заголовки на фронтенде через `next.config.js` (`headers()`). Недорого и безопасно добавить даже во время MVP — не меняет бизнес-логику.

Трудозатраты: 2–3 часа с проверкой, что CSP не ломает существующие страницы.

### 7. MEDIUM — VK OAuth: `state` не проверяется (login CSRF)

**Что нашёл.**
`GET /auth/vk/login` (`app/api/v1/auth.py`) генерирует `state = secrets.token_urlsafe(16)` и отдаёт его фронтенду вместе с `authorize_url`, но **нигде не сохраняет** (ни в Redis, ни в сессии/cookie).
`GET /auth/vk/callback` принимает только `code` и `parental_consent` — параметр `state` в сигнатуре эндпоинта вообще отсутствует, соответственно никогда не проверяется.
На фронтенде `axiom-frontend/app/auth/vk/callback/page.tsx` тоже не читает и не сверяет `state` из URL — только `code` и `error`.

Итого: `state` присутствует в коде как декоративный элемент — генерируется, но не участвует в проверке подлинности запроса.

**Риск.** Это классический «OAuth/login CSRF»: если атакующий сам пройдёт VK-авторизацию под своим VK-аккаунтом, получит свой `code`, и затем заманит жертву перейти по ссылке вида `https://axiom-mvp.relaxdev.ru/auth/vk/callback?code=<code_атакующего>` — браузер жертвы обменяет этот код и получит `TokenPair`, привязанный к **аккаунту атакующего**, который сохранится в `localStorage` жертвы. Жертва окажется залогинена в чужой (контролируемой атакующим) учётной записи, не заметив этого, и может, например, ввести туда персональные данные / результаты диагностики, думая, что это её личный кабинет — атакующий затем увидит эти данные под своим логином. Прямого захвата **аккаунта жертвы** это не даёт (в отличие от классической уязвимости, где такое связывание меняет чужой существующий аккаунт), но само по себе спутывание сессий — реальная, пусть и не самая тяжёлая, уязвимость аутентификации, к тому же затрагивающая несовершеннолетних пользователей.

Отдельно нужно отметить: `redirect_uri` при обмене кода (`exchange_code` в `vk_oauth.py`) берётся из серверного конфига (`settings.vk_redirect_uri`), а не от клиента — это правильно и закрывает более серьёзный класс атак (redirect_uri hijacking).

**Рекомендация:** сохранять `state` в Redis с коротким TTL (например, 10 минут) при `/vk/login`, требовать `state` как обязательный параметр `/vk/callback` и сверять его с сохранённым значением, удаляя после использования (тот же паттерн, что уже реализован для токена сброса пароля — переиспользовать существующий Redis).

Трудозатраты: 1–2 часа.

### 9. MEDIUM — согласие родителя как неверифицируемый чекбокс (152-ФЗ)

**Что нашёл.**
- Миграция `bc34a22e96af_add_parental_consent_fields_to_users.py`: добавляет `parental_consent_given: bool` (по умолчанию `false`) и `parental_consent_at: datetime`.
- `UserRegister` (`app/schemas/user.py`) требует `parental_consent: bool`, с валидатором, который **отклоняет** регистрацию (422), если `false` — это хорошо, поле действительно обязательное и на уровне API, а не только UI.
- `app/api/v1/auth.py`, `register()`: сохраняет `parental_consent_given=True` и текущую метку времени — **только если** Pydantic-валидатор уже пропустил запрос (то есть фактически поле всегда `True` на этом этапе; сам факт согласия проверяется раньше, в схеме).
- Для VK-регистрации (`vk_callback`) — то же самое, но `parental_consent: bool` передаётся **query-параметром** GET-запроса, значение `true` жёстко прописано на фронтенде (`axiom-frontend/app/auth/vk/callback/page.tsx`, строка с `URLSearchParams({ code, parental_consent: "true" })`) — отправляется только если пользователь отметил чекбокс в UI, но это, опять же, самозаявление, отправленное с клиента.
- Текст согласия («Я родитель/законный представитель… либо ученику уже исполнилось 14 лет и он действует с согласия родителя») зафиксирован дословно и на фронте, и (по данным `03-live-vs-code.md`) на проде.

**Честная оценка риска, без драматизации и без приукрашивания.**
Это **отметка о согласии**, а не **верификация личности** родителя/законного представителя: система никак не проверяет, что человек, поставивший галочку, действительно родитель, действительно совершеннолетний, и что для регистрирующегося ученика в принципе применимо исключение «уже 14 лет». Технически любой (включая самого ребёнка младше 14) может поставить галочку.

Это, тем не менее, **распространённая и юридически используемая практика** для MVP/пилотов в российском EdTech: 152-ФЗ не предписывает конкретный технический механизм верификации личности для получения согласия на обработку персональных данных — фиксация факта согласия (текст, чекбокс, timestamp) с последующей возможностью доказать его при необходимости (у нас есть `parental_consent_at`) — это минимально приемлемый, хотя и не идеальный, подход. Для **закрытого пилота**, где участники — заранее известные школьники/родители, с которыми есть внешняя, оффлайн договорённость об участии (что типично для пилотов через школу/учителя) — риск существенно ниже, чем для открытой публичной регистрации, потому что есть внешний, не-технический канал подтверждения согласия (сама школа/куратор пилота уже общается с родителями).

Чего не хватает даже для пилота:
- Нет ссылки на политику обработки персональных данных / согласие как отдельный юридический документ (в форме — только инлайн-текст чекбокса, не полноценный текст согласия по форме, которую обычно требует Роскомнадзор).
- Нет отдельного поля/способа зафиксировать контакт родителя (email/телефон) отдельно от ученика — то есть согласие даёт тот же email, что и логинится потом как «ученик».
- IP-адрес, с которого дано согласие, не сохраняется (только timestamp) — на случай будущего спора это было бы полезно.

**Рекомендация:**
1. Приемлемо для закрытого пилота **как есть**, при условии, что фактическое привлечение участников идёт через договорённость со школой/родителями вне продукта (что и заявлено в контексте задачи).
2. До перехода к открытому B2C — оформить полноценный текст согласия на обработку персональных данных как отдельный документ (не только чекбокс), с версионированием текста (что именно подписано, на какую дату — сейчас при изменении текста согласия задним числом непонятно, что именно подтвердил конкретный пользователь).
3. Недорогое усиление уже сейчас: логировать IP при согласии (1 доп. колонка + 10 строк кода), добавить ссылку на страницу с полным текстом политики.

Трудозатраты п.3: 1–2 часа. Юридическое оформление полноценного документа согласия — вне зоны инженерного аудита, нужен юрист.

### 10. MEDIUM — AI prompt injection и утечка данных через ИИ (риск на будущее, не сегодняшний)

**Что нашёл.** Сейчас `AI_SERVICE_MOCK=true` по умолчанию (`app/core/config.py`), `app/core/ai_client.py` в mock-режиме не делает сетевых вызовов вообще — просто подставляет фиксированный текст. Реального LLM в контуре нет, значит **сегодня** prompt injection физически некуда воткнуть — совет из брифа подтверждается: архитектурно ещё негде размещать защиту, потому что нет самого ИИ-вызова с интерполяцией.

Но `docs/ai-service-contract.md` уже описывает контракт для реального ИИ-сервиса («Валентины»): `POST /v1/assistant/chat` получает `user_id`, `subject`, `message` (сырой пользовательский ввод) и `history` (вся история диалога) и должен в ответ дать `answer`. Контракт **не описывает**:
- как формируется системный промпт на стороне ИИ-сервиса и как он защищён от переопределения через `message` пользователя (классический prompt injection: ученик пишет «игнорируй предыдущие инструкции и...»);
- политику модерации/безопасности вывода (что если ученик спросит что-то не относящееся к учёбе, оскорбительное, или попытается получить вредный контент — несовершеннолетний пользователь);
- политику хранения/логирования данных на стороне стороннего ИИ-сервиса — `history` содержит полную переписку ученика, включая потенциально чувствительный контент (ошибки, эмоциональные реакции), передаётся внешнему сервису от другой команды («Валентины») без описанного в контракте соглашения об обработке данных (аналог DPA) и без указания, где физически хостится модель (сам контракт упоминает тест на локальной модели Qwen2.5-3B — если в итоге используется сторонний облачный LLM API, а не self-hosted модель, персональные данные несовершеннолетних будут уходить к третьему облачному провайдеру, что для 152-ФЗ требует отдельного оформления);
- ограничение длины/частоты сообщений на входе в LLM-вызов отдельно от общего rate limiting (сейчас `POST /assistant/chat` защищён только общей аутентификацией, никакого лимита на количество AI-вызовов в час на пользователя нет — при реальном (платном) ИИ это ещё и прямой финансовый риск: один пользователь может исчерпать бюджет на LLM API за минуты).

**Рекомендация — что заложить ДО подключения реального ИИ (не блокер для текущего mock-пилота, но обязательный пункт бэклога перед переключением `AI_SERVICE_MOCK=false`):**
1. Чёткое разделение system prompt / user input на стороне ИИ-сервиса (структурированные роли, а не конкатенация строк) — зона ответственности «Валентины», но должно быть явно прописано в контракте как требование.
2. Rate limit на `/assistant/chat` по пользователю (например, N сообщений в час) — недорого, тот же Redis-паттерн, что и везде.
3. Базовая модерация вывода (фильтр на явно неприемлемый контент) перед показом ответа несовершеннолетнему пользователю.
4. Явно зафиксировать в контракте: где хостится модель, кто имеет доступ к логам диалогов, срок хранения истории чата, и то, что это персональные данные несовершеннолетних, требующие того же уровня защиты, что и остальная БД.
5. Ограничение длины `message` на входе (сейчас `ChatRequest.message` — нужно проверить schemas/assistant.py на наличие `max_length`; не найдено ограничения в просмотренном коде — стоит добавить, это и защита от prompt-injection-через-объём, и от злоупотребления бюджетом на токены).

Трудозатраты: это не код сейчас, а требования к контракту и бэклог перед интеграцией реального ИИ — фиксация в `docs/ai-service-contract.md` может быть сделана за 1–2 часа обсуждения с командой ИИ-сервиса.

Это прямо противоречит осознанному решению для `/auth/password-reset/request`, где намеренно всегда возвращается одинаковый `202` независимо от того, найден email или нет (это даже явно откомментировано в коде как защита от перебора).

**Риск.** Низкий — позволяет злоумышленнику перебором проверить, какие email зарегистрированы в системе (например, для последующего таргетированного фишинга учеников). Не даёт доступа к паролю/токену, ограничено rate limit на регистрацию (5/час/IP — с оговоркой по п. 3 о прокси).

**Рекомендация:** для MVP можно оставить (UX регистрации обычно требует сообщать о дубликате email, это общепринятый компромисс), но стоит явно решить и задокументировать: если приоритет — минимизация enumeration, можно вместо 409 отправлять письмо «на этот email уже зарегистрирован аккаунт» и возвращать нейтральный ответ похожий на успешную регистрацию. Не блокер.

Трудозатраты: 30 минут, если решат менять поведение.

---

### 13. LOW — токен сброса пароля в логах при неполной SMTP-конфигурации

**Что нашёл.** `app/core/email.py`, `send_password_reset_email()`: если `settings.smtp_host` пусто — `logger.info("Письмо восстановления пароля для %s: %s", to_email, reset_link)`, где `reset_link` содержит сам одноразовый токен сброса пароля в открытом виде.

**Риск.** Это осознанный dev-fallback (явно описано в комментариях файла) — чтобы флоу сброса пароля можно было тестировать локально без настройки SMTP. Риск возникает только если на проде `SMTP_HOST` не будет настроен (тогда токены сброса будут литься в логи контейнера, доступные всем, у кого есть доступ к логам/хостингу) — на проде `03-live-vs-code.md` фиксирует это как **UNKNOWN**: реальное значение `SMTP_HOST` на проде аудиту недоступно.

**Рекомендация:** явно подтвердить на проде, что `SMTP_HOST` настроен (иначе восстановление пароля для реальных пользователей и так не будет работать — это в равной степени функциональный баг). Дополнительно — рассмотреть понижение уровня чувствительности лога даже в dev-режиме (например, логировать факт отправки без самого токена, а токен выводить только в явном DEBUG-режиме) — не обязательно для MVP.

Трудозатраты: 15 минут на проверку конфигурации прода владельцем.

---

### 14. LOW — email не верифицируется при регистрации

**Что нашёл.** `UserRegister` не требует подтверждения владения email — учётная запись создаётся сразу, `password-reset` работает по указанному email без проверки, что он вообще принадлежит регистрирующемуся.

**Риск.** Низкий для текущего масштаба (закрытый пилот). Кто-то может зарегистрироваться на чужой email, но без доступа к почте не сможет ни подтвердить, ни как-либо использовать чужой адрес во вред — максимум, спам самому себе. Основной сценарий, где это важно, — гарантия, что канал для сброса пароля/уведомлений действительно принадлежит ученику/родителю.

**Рекомендация:** не блокер для пилота; для коммерческого запуска — добавить email-верификацию (тот же паттерн токена, что уже есть для password-reset, можно переиспользовать).

Трудозатраты: 2–3 часа, если решат делать.

---

### 15. LOW — фингерпринтинг стека через заголовки

**Что нашёл.** На проде подтверждены заголовки `Server: uvicorn` (бэкенд) и `X-Powered-By: Next.js` (фронтенд) — раскрывают технологический стек анонимному наблюдателю.

**Риск.** Минимальный сам по себе, слегка облегчает разведку для целенаправленной атаки (знание версии/фреймворка сужает выбор известных уязвимостей). Не является приоритетом.

**Рекомендация:** убрать/переопределить на уровне reverse-прокси (`proxy_hide_header Server`, `poweredByHeader: false` в `next.config.js`) — 15 минут, можно сделать заодно с п. 6.

## Позитивные находки (что уже сделано правильно)

Чтобы не создавать ложного впечатления, что в проекте всё плохо — ниже то, что реализовано корректно и не требует исправлений:

1. **Хеширование паролей** — `passlib` с `bcrypt` (`app/core/security.py`), адаптивный алгоритм с солью, стандарт индустрии. Открытый пароль нигде не хранится и не логируется — grep по `logger`/`logging` во всём backend не нашёл ни одного места, где логировался бы пароль или токен вне уже описанного в п. 13 dev-fallback.
2. **IDOR защита реально работает, не только в тестах.** Во всех проверенных местах (`app/api/v1/diagnostics.py`: `/answer`, `/{session_id}/finalize`, `/{session_id}/result`; `app/api/v1/assistant.py`: `/chat`, `/sessions/{id}/history`) код явно проверяет `session.user_id != user.id` и возвращает `404` (не `403`, что дополнительно не подтверждает даже существование чужой сессии) при попытке доступа к чужим данным. Тесты `test_other_user_cannot_access_session` в `tests/test_diagnostics.py` и `tests/test_assistant.py` — не просто заглушки, они реально создают второго пользователя, логинятся и убеждаются в `404`. Это соответствует утверждению задания и подтверждено чтением кода, а не только тестов.
3. **Rate limiting присутствует на всех чувствительных auth-эндпоинтах**: регистрация, логин (по IP и по email отдельно), запрос и подтверждение сброса пароля, VK callback — реализовано на Redis без лишних зависимостей, с корректным `Retry-After`. Ограничение по email отдельно от IP — хорошее архитектурное решение, которое продолжит работать даже при проблеме из п. 3 (прокси).
4. **CORS настроен строго** — `allow_origins=[settings.frontend_url]`, единственный known-origin, не wildcard `*`, подтверждено и в коде, и preflight-запросом на проде.
5. **Правильный выбор Bearer-токена вместо cookie** убирает CSRF как класс атак для самого API (см. обсуждение trade-off в п. 4).
6. **Ответ на задание сброса пароля не палит существование email** (`password-reset/request` всегда `202`) — осознанная, откомментированная защита от перебора, тестами подтверждено (`test_password_reset_unknown_email_still_202`).
7. **Токен сброса пароля одноразовый** — `redis.delete(key)` сразу после успешного использования, повторное использование того же токена даёт `400` (подтверждено тестом `test_password_reset_full_flow`, включая проверку `reuse.status_code == 400`).
8. **Правильные ответы (`access`/`refresh`) различаются по `type` в самом JWT-payload** (`app/core/security.py`, `get_current_user` в `auth.py` явно проверяет `payload.get("type") != "access"`) — refresh-токен, даже если бы использовался, не может быть подсунут вместо access-токена.
9. **Правильный ответ трейнера** — `TrainerTaskOut` явно исключает `correct_answer`/`explanation` до ответа ученика (см. комментарий в `app/schemas/trainer.py`: «Без correct_answer и explanation — их отдаём только после ответа»), проверка корректности выполняется на сервере (`app/core/answer_check.py`), а не доверяется клиенту.
10. **RBAC отсутствует, но и не требуется на этом этапе** — в системе нет ролей/админки/привилегированных действий вообще (только «ученик» видит только свои данные), поэтому отсутствие RBAC — не пробел, а корректное отражение того, что продукту пока нечем управлять с повышенными правами. Если в будущем появится роль «учитель»/«админ школы» — тогда потребуется полноценная модель ролей, сейчас её отсутствие не создаёт риска.
11. **`redirect_uri` в VK OAuth фиксирован на сервере**, а не принимается от клиента — закрывает redirect_uri hijacking (частичная защита в дополнение к недостающей проверке `state`, см. п. 7).

## Executive Summary

AXIOM в текущем виде — типичный ранний MVP: базовые механизмы аутентификации, авторизации и защиты от перебора реализованы аккуратно и по существу корректны (bcrypt, честная проверка владения сессией/чатом против IDOR, продуманный rate limiting, безопасный CORS), включая honest-by-design детали вроде одинакового 202-ответа на сброс пароля независимо от существования email. Одновременно найдены две проблемы уровня CRITICAL, обе — не в бизнес-логике аутентификации, а в конфигурации репозитория и инфраструктуры: `.env` отслеживается git без `.gitignore` (структурный риск утечки секретов, и неясно, не работает ли прод прямо сейчас с дефолтным `JWT_SECRET` — это требует немедленной ручной проверки владельцем, не откладывая) и Postgres/Redis потенциально доступны напрямую из интернета со слабыми/отсутствующими учётными данными через `docker-compose.yml`. Ни один из CRITICAL-пунктов не подтверждён как реально эксплуатируемый на живом проде в рамках этого аудита (для этого нужен доступ к прод-`.env` и сетевое сканирование прод-хоста, что вне полномочий статического аудита) — но оба тривиально проверяемы владельцем за 15–30 минут и должны быть закрыты до пилота, а не после. Отдельно стоит риск rate limiting за реверс-прокси RelaxDev (HIGH) — если прокси не пробрасывает реальный IP клиента, регистрация и VK-вход рискуют случайно заблокироваться для всего пилота, а не только для атакующего. Согласие родителя как неверифицируемый чекбокс — юридически приемлемо для закрытого пилота с внешней (оффлайн) договорённостью со школой/родителями, но не готово к открытому B2C. AI prompt injection сегодня неактуален (ИИ — заглушка), но контракт с реальным ИИ-сервисом должен заранее оговорить защиту от инъекций, модерацию и обработку персональных данных несовершеннолетних до переключения `AI_SERVICE_MOCK=false`.

## Вердикт: можно ли пилотировать на 100 школьниках?

**Условно да — при обязательном закрытии двух CRITICAL-пунктов перед стартом, остальное не блокирует пилот.**

Блокеры (должны быть закрыты **до** открытия пилота, каждый — часы, не дни):
1. Подтвердить и при необходимости ротировать `JWT_SECRET`/`VK_CLIENT_SECRET`/`SMTP_PASSWORD` на проде + добавить `.gitignore` и убрать `.env` из индекса git (п. 1).
2. Подтвердить, что Postgres (5432) и Redis (6379) не достижимы из интернета на прод-хосте; если достижимы — закрыть портами/файрволом и сменить пароль БД с `axiom`/`axiom` на случайный, задать пароль Redis (п. 2).

Настоятельно рекомендуется закрыть до пилота, но не блокер при явном осознанном риске: проверить поведение rate limiting за реальным прокси на регистрации/VK (п. 3) — иначе есть шанс сорвать день открытия пилота массовой блокировкой регистраций.

Всё остальное (localStorage-токен, отсутствие logout-инвалидации, security-заголовки, VK state, публичный Swagger, консент-чекбокс) — реальные, но некритичные для закрытого пилота на 100 известных пользователей находки, которые стоит закрывать по приоритету в течение MVP-этапа, не откладывая на неопределённый срок, но и не как условие запуска.
