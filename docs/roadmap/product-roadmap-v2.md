Опирается на `docs/product/05-feature-prioritization.md` (что делать), `docs/product/04-killer-feature.md` (что первично), `docs/product/oge-knowledge-graph.md` (объём контента) и трёхэтапную архитектуру `docs/architecture/02-target-architecture.md` (если создан в рамках Фазы 14: Stage 1 ~100 пользователей, Stage 2 1 000–10 000, Stage 3 масштаб).

## Как читать роадмап

Шесть горизонтов: **NOW → MVP → MVP+ → Launch → V1 → Scale**. Для каждой фичи — приоритет (из `05-feature-prioritization.md`), ценность, усилия, риск, зависимости. Горизонты — не фиксированные календарные даты (это отдельно в `docs/roadmap/90-day-plan.md` для первых 90 дней), а последовательность, в которой решения логически зависят друг от друга. Ничего в MVP+ не должно начинаться раньше завершения блокирующих пунктов NOW — это намеренное ограничение, а не бюрократия: главная находка аудита (`01-product-audit.md`) — продукт уже один раз пострадал от показа нереализованной функциональности как готовой, повторять это в ускоренном темпе на новых фичах — тот же риск в новой форме.

## Горизонт NOW (немедленно, до/вместе с любым публичным трафиком)

Цель горизонта: остановить активный вред от фиктивной функциональности и создать возможность измерять последующие решения.

| Фича | Приоритет | Ценность | Усилия | Риск | Зависимости |
|---|---|---|---|---|---|
| Честно пометить/скрыть фиктивные данные диагностики и ИИ-ассистента | P0 | Высокая (доверие, этика для несовершеннолетних) | Низкие (UI-изменение, без новой логики) | Низкий | Нет |
| Исправить баг мобильного логаута (`hidden md:block`) | P0 | Высокая (безопасность аккаунта) | Низкие (одна строка CSS/разметки) | Низкий | Нет |
| Внедрить минимальную аналитику событий | P0 | Высокая (без неё невозможно измерить остальной роадмап) | Средние (новая таблица/сервис, интеграция по всем экранам) | Низкий | `docs/product/analytics-spec.md` |

## Горизонт MVP (доказать первый честный слой адаптивности на ~100 пользователях)

Цель горизонта: заменить фиктивный прогресс на реальный, детерминированный, не дожидаясь готового ИИ-сервиса — соответствует Stage 1 целевой архитектуры (~100 пользователей).

| Фича | Приоритет | Ценность | Усилия | Риск | Зависимости |
|---|---|---|---|---|---|
| Живая карта навыков (Skill Mastery Map, killer feature) | P1 | Максимальная (25/30 по методике `04-killer-feature.md`) | Средние (skill graph + правила обновления, без ML) | Низкий (детерминированная логика, тестируема) | Формализация графа тем/навыков (`oge-knowledge-graph.md`, раздел 5, пункт P0) |
| Формализовать граф навыков в данных (таблицы `topics`/`skills`/`skill_prerequisites`) | P1 | Высокая (фундамент для карты навыков и будущей диагностики) | Средние (миграции БД, без нового UI) | Низкий | `docs/architecture/03-database-design-v2.md` (если создан) |
| Публичный лендинг | P1 | Высокая (блокирует органическое привлечение) | Низкие-средние (статический маркетинговый экран) | Низкий | Нет |
| Онбординг («что это, зачем диагностика, что дальше») | P1 | Высокая (снижает отказ на первом сеансе для 14–16 лет) | Низкие-средние | Низкий | Нет |
| Канал обратной связи пользователь → команда | P1 | Высокая (единственный сигнал от первых 100 пользователей) | Низкие (форма + таблица) | Низкий | Нет |
| Сузить/предупредить о несоответствии класса и контента | P1 | Средняя (честность формы) | Низкие | Низкий | Нет |
| Расширить банк тренажёра по графу знаний (русский: синтаксис/лексика; математика: геометрия как текстовые задачи) | P1 | Средняя-высокая (объём практики под картой навыков) | Средние (контентная работа, педагогическая проверка) | Низкий | `oge-knowledge-graph.md`, участие педагога (Валерия, по README/коду) |

## Горизонт MVP+ (углубление адаптивности, всё ещё без обязательного ИИ)

Цель горизонта: сделать карту навыков полезной для планирования, начать готовить контур для реального ИИ-сервиса параллельно (работа Data Scientist), не блокируя остальной продукт её готовностью.

| Фича | Приоритет | Ценность | Усилия | Риск | Зависимости |
|---|---|---|---|---|---|
| Персональный план с дедлайном до экзамена | P2 | Высокая для родителя-плательщика («у ребёнка есть план») | Средние (детерминированное распределение навыков по неделям) | Низкий | Карта навыков (MVP), даты экзамена по региону (НЕИЗВЕСТНО без проверки Рособрнадзора) |
| Явное решение по странице цен | P2 | Средняя (снимает неопределённость монетизации) | Низкие (решение + при необходимости заглушка экрана) | Низкий | `docs/business/business-model-v2.md` (если создан) |
| Явное решение по pgvector (использовать под RAG или убрать) | P2 | Низкая напрямую, средняя как гигиена инфраструктуры | Низкие | Низкий | Решение по AI Tutor / RAG (`docs/architecture/ai-tutor.md`, если создан) |
| Параллельный трек: рабочий ИИ-сервис в разработке (latency/качество измеряются, не встраиваются в продукт до готовности) | P2 (инфраструктурно) | Высокая в перспективе | Высокие (RAG/промпт-инжиниринг/эксперименты по latency) | Средний-высокий (эксперимент Qwen2.5-3B — 38.4 сек на CPU при требовании ≤5 сек) | `docs/architecture/ai-tutor.md` (если создан), работа Data Scientist (Валентина, по коду/контракту) |

## Горизонт Launch (коммерческий запуск, Stage 2 целевой архитектуры, ~1 000–10 000 пользователей)

Цель горизонта: первое реальное использование ИИ-функционала в продукте — узко, экономично, только там, где качество и latency уже подтверждены измерениями (не декларацией).

| Фича | Приоритет | Ценность | Усилия | Риск | Зависимости |
|---|---|---|---|---|---|
| Explain-my-mistake (узкое ИИ-объяснение конкретной ошибки) | P2 | Высокая (момент максимальной вовлечённости ученика) | Средние (узкий структурированный промпт, не открытый диалог) | Средний (качество/latency, но контролируемый объём запроса) | Рабочий, измеренный ИИ-сервис (latency ≤5 сек подтверждена на реальной инфраструктуре, не только в эксперименте) |
| Монетизация (если решение MVP+ было «да») | P1 (при принятом решении) | Высокая (первая выручка) | Средние (биллинг, тарифы) | Средний (см. `docs/business/business-model-v2.md`, если создан) | Событие `subscription_started` в аналитике уже готово (заложено в `analytics-spec.md`) |
| Реальная CAT/IRT-диагностика | P3 | Высокая (доверие к диагностике) | Высокие (статистическая калибровка, нужен более широкий банк заданий) | Средний (неверная калибровка = недостоверный результат, менее очевидный, чем сегодняшняя заглушка) | Расширенный банк заданий (десятки-сотни калиброванных заданий на тему, не 45) |

| Фича | Приоритет | Ценность | Усилия | Риск | Зависимости |
|---|---|---|---|---|---|

## Горизонт Scale (Stage 3 целевой архитектуры, 10 000 → 100 000 → 500 000+)

На этом горизонте роадмап намеренно не детализируется по фичам — правильный набор фич для масштаба определяется данными, накопленными на Launch/V1, а не заранее. Единственное, что фиксируется сейчас: **не начинать инвестировать в эти пункты, пока триггеры масштабирования из `docs/architecture/02-target-architecture.md` (если создан) не достигнуты** — прямое применение принципа CLAUDE.md «не оптимизировать преждевременно под сотни тысяч пользователей».

Кандидаты, требующие данных для решения (не факты, а вопросы, на которые Launch/V1 должны дать ответ): мобильное приложение или Telegram-бот (нужен спрос, а не гипотеза), RAG/векторный поиск по учебникам и ФИПИ (нужна подтверждённая ценность explain-my-mistake без RAG сначала), Deep Knowledge Tracing / RL-планировщик (нужна накопленная история попыток на масштабе, которой сегодня физически не существует), B2B/школьный трек (нужен отдельный custdev, не входит в текущий фокус B2C).

## Явно НЕ строить сейчас (антипереусложнение)

Список фич, отклонённых или отложенных с явным обоснованием «зачем не сейчас» (перекрёстная ссылка на `docs/product/05-feature-prioritization.md`, раздел 2, POSTPONE):
- Мобильное приложение / Telegram-бот — нет подтверждённого спроса, веб уже выбран точкой входа.
- RAG / векторная БД (несмотря на то, что образ pgvector уже в `docker-compose.yml`) — до подтверждения ценности explain-my-mistake без RAG.
- Deep Knowledge Tracing / RL-планировщик — заявлены в питч-деке, но требуют данных, которых при 100 пользователях физически не может накопиться в статистически значимом объёме.
- Микросервисная декомпозиция бэкенда — текущий монолит FastAPI + отдельный AI-сервис по контракту уже даёт разделение по реальной причине (разные владельцы/технологии команды); дальнейшее дробление не обосновано нагрузкой на Stage 1–2.
