# Фаза 7 — Направления дизайна AXIOM

Статус: АУДИТ / ПРЕДЛОЖЕНИЕ. Ни одно направление не реализовано в коде — это дизайн-гипотезы для обсуждения, вытекающие из честной оценки в `docs/product/01-product-audit.md` (ИИ-функционал — заглушка) и `docs/product/02-ux-ui-audit.md`.

## Как выбирались направления

Ключевое ограничение, определяющее выбор направлений: **настоящий ИИ-сервис не задеплоен**, а офлайн-эксперимент с Qwen2.5-3B даёт 38.4 сек на CPU при требовании ≤5 сек — то есть «ИИ 24/7, отвечающий за 5 секунд» на сегодня не инженерный факт, а цель. Любое направление, которое ставит ИИ-диалог в центр первого экрана, наследует этот риск напрямую. Поэтому ниже даны три направления с разной степенью зависимости от ИИ, чтобы решение о направлении было осознанным, а не унаследованным от питч-дека по умолчанию.

---

## Направление A: AI-first

**Идея:** ИИ-ассистент — главный экран и точка входа. Ученик сразу попадает в чат, объясняет, что не понимает, получает разбор «на пальцах», диагностика и тренажёр — вспомогательные инструменты, которые чат вызывает по мере необходимости («давай проверим, закрепилось ли» → короткая серия заданий внутри чата).

- **Дашборд:** минимальный — сводка «о чём мы говорили в последний раз», без отдельного экрана прогресса на первом плане.
- **Навигация:** чат как домашний экран; диагностика/тренажёр — как результат действий внутри диалога, а не отдельные пункты меню первого уровня.
- **Онбординг:** «расскажи, с чем сложности» — разговорный, без форм.
- **Основной флоу:** вопрос ученика → объяснение → мини-практика внутри чата → фиксация в знании темы.
- **Визуальное направление:** тёплый, разговорный, минимум таблиц и процентов на экране, акцент на тексте и диалоге.
- **Плюсы:** прямое попадание в заявленное УТП питч-дека («ИИ-репетитор 24/7»); при рабочем ИИ — максимально дифференцирующий опыт против Решу ОГЭ (там чата нет).
- **Минусы:** полностью зависит от компонента, которого сегодня не существует в продакшене (реальный ИИ-сервис не задеплоен, задержка ответа на CPU в 7+ раз выше требования); при заглушке или медленном ответе — это направление, где обман ожиданий пользователя максимален, потому что вся ценность экрана сводится к качеству и скорости ответа.
- **Сложность реализации:** высокая — требует рабочего RAG/LLM-контура, оценки качества (hallucination risk), latency-инженерии, безопасности от prompt injection (см. `docs/architecture/ai-tutor.md`).
- **Retention:** потенциально высокий, если ИИ реально полезен и быстр; потенциально нулевой или отрицательный (отток после первого разочарования), если нет.
- **Монетизация:** естественно ложится на лимиты сообщений/тарифы по объёму диалога — понятная для пользователя модель («бесплатно N вопросов в день»).

## Направление B: Exam-first

**Идея:** Продукт организован вокруг структуры самого экзамена ОГЭ — кодификатор ФИПИ как каркас навигации, а не «предмет → случайная тема». Главный экран — карта экзамена (часть 1/часть 2, по каждому заданию — типовая формулировка, статус освоения), тренажёр и диагностика достраиваются вокруг этой карты. ИИ — вспомогательная функция («объясни это задание»), не точка входа.

- **Дашборд:** карта экзамена в духе «29 из 25 заданий ОГЭ математика — статус по каждому» (см. `docs/product/oge-knowledge-graph.md`), а не абстрактный % по предметам.
- **Навигация:** по структуре экзамена (часть 1 / часть 2 / типы заданий), а не по предметам верхнего уровня.
- **Онбординг:** «когда экзамен» → «вот структура» → «начнём с диагностики по частям экзамена».
- **Основной флоу:** диагностика по формату экзамена → карта пробелов по конкретным номерам заданий → тренажёр по конкретному типу → повтор.
- **Визуальное направление:** структурное, табличное, с явным прогресс-баром по 25 заданиям (математика) — близко к тому, что уже привычно ученику по Решу ОГЭ/официальным демоверсиям, снижает когнитивную нагрузку на знакомство с интерфейсом.
- **Плюсы:** не зависит от рабочего ИИ вообще — можно построить полностью на детерминированной логике (совпадает с принципом CLAUDE.md «предпочитать rule-based решения на MVP»); реализуемо в ближайшие недели, а не месяцы; ясная, проверяемая метрика прогресса («8 из 25 типов заданий освоены»).
- **Минусы:** менее «вау»-эффектно для инвестора/питча, так как не выглядит как «ИИ-продукт»; выше риск слиться с Решу ОГЭ по восприятию, если не добавить явную персонализацию поверх структуры.
- **Сложность реализации:** низкая-средняя — в основном контентная работа (наполнение карты по кодификатору) и UI, минимум ML.
- **Retention:** средний, управляемый явной механикой «закрой оставшиеся N заданий до экзамена» (дедлайн-ориентированная мотивация, актуальная именно для 9 класса).
- **Монетизация:** тарифы по объёму контента/полноте карты (например, бесплатно — часть 1, платно — часть 2 с разбором критериев).

## Направление C: Adaptive-first

**Идея:** Центр продукта — видимая ученику модель его знаний (skill state), которая обновляется после каждой попытки, и рекомендация «что решать дальше» — прозрачная, объяснимая, видимая как причинно-следственная связь («ты ошибся в X → предлагаем Y»), сначала на **простых, детерминированных правилах** (см. `docs/architecture/adaptive-learning-engine.md`), без ML на MVP. ИИ и структура экзамена — вторичны по отношению к «показать ученику, что система реагирует на его конкретные ошибки».

- **Дашборд:** карта навыков (skill graph) с цветовой индикацией уровня владения по каждому навыку, обновляемая после каждой попытки — не статичный % с диагностики раз в месяц, а живой, меняющийся после каждого решённого задания в тренажёре.
- **Навигация:** «твой следующий шаг» как главный CTA, выведенный из явного, объяснимого правила, а не абстрактное меню предметов.
- **Онбординг:** короткая диагностика (не 45 минут — сокращённая, 10–15 заданий по ключевым навыкам) → сразу видимое обновление карты навыков → первое «следующее задание» с объяснением, почему оно выбрано.
- **Основной флоу:** попытка → мгновенное обновление модели знания → прозрачная рекомендация следующего задания → повтор; диагностика становится не разовым событием, а continuous-процессом.
- **Визуальное направление:** визуализация графа/карты навыков, акцент на прогресс-индикаторах уровня владения на уровне отдельного навыка, а не только предмета в целом.
- **Плюсы:** реализуемо детерминированно на MVP (без ML) в соответствии с принципом CLAUDE.md; напрямую чинит главную сегодняшнюю проблему продукта — фиктивность диагностики/прогресса (см. Фазу 5); прозрачность рекомендаций («почему это задание») — сама по себе UX-инновация, которую не делает ни один прямой конкурент.
- **Минусы:** требует переосмысления модели данных (skill graph с пререкизитами — см. `docs/architecture/adaptive-learning-engine.md` и `docs/architecture/03-database-design-v2.md`), не просто косметика поверх текущих экранов; на очень раннем этапе (мало попыток на ученика) рекомендации могут быть неустойчивыми/скудными данными.
- **Сложность реализации:** средняя — основная работа не в ML, а в проектировании и наполнении графа знаний и правил обновления состояния; технически ближе к тому, что уже частично есть (правило выбора темы в тренажёре), чем к направлению A.
- **Retention:** потенциально высокий и устойчивый — визуальный, постоянно обновляющийся прогресс является одним из самых проверенных механизмов удержания в EdTech (Duolingo-подобный паттерн), не зависящим от качества генеративного ИИ.
- **Монетизация:** тарифы по глубине аналитики/охвату навыков либо по скорости продвижения (например, платный ускоренный режим с расширенной практикой по слабым навыкам).

## Сравнительная таблица

| Критерий | A. AI-first | B. Exam-first | C. Adaptive-first |
|---|---|---|---|
| Зависимость от рабочего ИИ-сервиса | Полная (блокер) | Минимальная | Минимальная |
| Совпадение с текущим кодом/данными | Низкое | Среднее | Высокое (тренажёр уже частично так работает) |
| Время до пилотной версии | Месяцы (ждёт ИИ-сервис) | Недели | 3–4 недели |
| Риск обмана ожиданий пользователя | Высокий | Низкий | Низкий |
| Дифференциация от Решу ОГЭ | Высокая (если работает) | Низкая-средняя | Высокая |
| Соответствие принципу CLAUDE.md «rule-based на MVP» | Нарушает | Соблюдает | Соблюдает |
| Инвесторская «эффектность» с первого взгляда | Высокая | Низкая | Средняя-высокая (визуально) |

## Рекомендация

**Рекомендуемое направление: C — Adaptive-first**, с элементами B (структура экзамена как каркас графа знаний), при этом A (AI-first) не отбрасывается, а откладывается до момента, когда ИИ-сервис Data Scientist'а реально задеплоен, измерен по latency/качеству и готов встраиваться поверх уже работающей модели знаний ученика.

Обоснование:
1. Adaptive-first напрямую устраняет главный найденный дефект продукта — фиктивность диагностики и прогресса (Фаза 5, Фаза 6) — без необходимости ждать ИИ-сервис.
2. Соответствует принципу CLAUDE.md «предпочитать детерминированные решения на MVP, когда этого достаточно» — карта навыков и правила рекомендаций можно построить без ML.
3. Даёт настоящую, проверяемую причину для ежедневного возврата (обновляемая карта навыков), которой сегодня нет вообще (см. п. 4 в `01-product-audit.md`).
4. Оставляет ИИ-ассистента и exam-структуру как совместимые надстройки, а не конкурирующие архитектуры: когда ИИ-сервис будет готов, он естественно встраивается как объяснение к конкретному навыку/заданию внутри уже существующей карты, а структура экзамена (B) становится верхним слоем группировки навыков.

Направление A не выбирается как основное **не потому, что ИИ не важен**, а потому что строить главный экран продукта вокруг компонента, для которого нет ни задеплоенного сервиса, ни подтверждённой latency в рамках требований (≤5 сек), — прямое нарушение принципа CLAUDE.md «не строить фичи ради технической привлекательности» и высокий риск повторить сегодняшнюю ошибку (интерфейс поверх несуществующей функции) в новой обёртке.
