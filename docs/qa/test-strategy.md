## Рекомендуемая стратегия по стадиям

### MVP (сейчас) — минимально достаточно, не избыточно

1. **CI, гоняющий уже существующее** — единственная по-настоящему срочная рекомендация. У проекта уже ЕСТЬ 33 backend-теста и чистый typecheck фронтенда — но они не подключены ни к какому автоматическому гейту, поэтому серия `Revert`-коммитов в истории могла случиться именно потому, что проверить деплой перед мержем было некому. Минимальный пайплайн: GitHub Actions, сервисы `postgres` + `redis`, шаги `pytest`, `npm run build`, `tsc --noEmit`. Один день работы, немедленная отдача.
2. **Один сквозной E2E-тест** (Playwright): регистрация → диагностика → тренажёр → дашборд, на CI против поднятого docker-compose стека. Не полное покрытие — один тест, ловящий класс проблем «страница технически рендерится, но реальный клик по кнопке ничего не делает» (сейчас проверяется только вручную самим владельцем, по признанию README).
3. **Ручной чек-лист регресса перед каждым релизом** (пока нет полного E2E-покрытия) — короткий список: регистрация с согласием/без, логин, ошибка входа, диагностика по обоим предметам, тренажёр — верный/неверный ответ, ассистент — отправка сообщения, дашборд отображает прогресс, мобильная раскладка (в т.ч. видимость logout — известный баг).
4. **`.eslintrc`** — 5 минут, `next/core-web-vitals`.

### Launch (коммерческий запуск)

- Backend lint/typecheck (`ruff`+`mypy`) в CI.
- AI evaluation как повторяемый процесс: golden-датасет вопросов ОГЭ (математика + русский) с эталонными ответами/критериями, автоматический прогон при каждой смене модели/промпта, отслеживание точности/латентности/стоимости во времени — не разовый тест, а регрессионный набор.
- Нагрузочное тестирование auth-эндпоинтов (проверить, что rate limiting реально работает за реверс-прокси — см. `docs/security/security-audit.md`, находка 1).
- Тесты платёжного флоу (когда появится биллинг) — с песочницей провайдера.

### Scale

- Полное покрытие E2E критических путей.
- Визуальная регрессия, если дизайн-система усложнится (многокомпонентная библиотека).
- Continuous AI eval как часть релизного процесса ИИ-сервиса, с порогами качества, блокирующими деплой при регрессии точности.

## Явный принцип (в духе CLAUDE.md)

Не наращивать тестовую пирамиду ради полноты — для 100 пользователей и одного разработчика полное покрытие unit-тестами фронтенда является overkill; гораздо дешевле и эффективнее один сквозной E2E-тест + CI, гоняющий уже написанные 33 backend-теста, которые сейчас существуют, но бесполезны без автоматического запуска.
