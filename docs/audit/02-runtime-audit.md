# 02 — Раннтайм-аудит (Фаза 2)

> Среда аудита: Windows 10, без доступа к работающему Docker daemon (Docker Desktop установлен, но `docker info`/`docker ps` не смогли подключиться к `npipe:////./pipe/dockerDesktopLinuxEngine` — демон не запущен, WSL-дистрибутив `docker-desktop` в состоянии Stopped, попытка запуска через `Docker Desktop.exe` не подняла демон за время аудита) и без доступного Redis. Node v24.13.0, Python 3.12/3.13. Локально установлен системный PostgreSQL 18 (служба `postgresql-x64-18` в состоянии RUNNING), но это сторонняя инсталляция с неизвестными учётными данными, не связанная с `docker-compose.yml` проекта (там — `pgvector/pgvound:pg16`, роль `axiom`/`axiom`); подключение на порт 5432 отклонено (connection refused) — не тот процесс/порт слушает, диагностика стороннего Postgres не входила в объём аудита. Дата: 2026-09-11.

## Итог одной строкой

Обе кодовые базы (frontend, backend) **устанавливаются и статически проверяются без ошибок**. Полный сквозной runtime-прогон (`docker compose up`, backend-тесты против реальной Postgres+Redis, ручной клик-тест в браузере) в этой среде технически невозможен — не хватает работающего Docker и Redis. Это ограничение среды аудита, а не подтверждённый баг продукта — и симптоматично, что то же самое ограничение («здесь физически недоступен Docker») README проекта фиксирует и у самого разработчика: `docker compose up --build` ни разу не было прогнано целиком ни при разработке, ни в этом аудите. Это второе независимое подтверждение одной и той же проблемы — процесс верификации перед деплоем в проекте не автоматизирован (нет CI), и полагается на ручной прогон, который дважды подряд оказался никем не выполнен целиком.

## Сценарий Landing → Registration → Login → Onboarding → Diagnostic → Dashboard → Practice → Answer → Error → AI Tutor → Progress

Пройден **по коду** (чтение исходников всех экранов и API) и **частично на живом MVP** (только неразрушающие GET/OPTIONS-запросы — правила аудита запрещают создавать тестовые данные на проде). Итог по каждому шагу:

1. **Landing** — отсутствует как таковой. `/` — клиентский компонент, показывает только «Загрузка…» и мгновенно редиректит на `/login` или `/dashboard`. Публичного описания продукта, цен — нет нигде до входа. Подтверждено и по коду, и запросом на прод.
2. **Registration** — работает: email, пароль ≥8 симв., класс, обязательный чекбокс согласия родителя (152-ФЗ). Подтверждено на проде: запрос с невалидным email/коротким паролем вернул корректный `422` с точными сообщениями валидации, без побочных эффектов (проверка — до обращения к БД).
3. **Login** — по коду работает, есть rate limit (8/15мин по IP + 5/15мин по email → `429` + `Retry-After`). `/login` на проде рендерится 1:1 с кодом.
4. **Onboarding** — **отсутствует как отдельный шаг**. После регистрации — сразу `/dashboard` без объяснения интерфейса/целей, кроме одной карточки «Пройдите входную диагностику».
5. **Diagnostic** — сессия/ответы/результат реально сохраняются, но **вопросы и итог — захардкоженная заглушка**, не зависящая от ответов ученика (детали — `03-live-vs-code.md`, `04-documentation-gap-analysis.md`). Дополнительно найден баг заглушки: `_MOCK_ITEMS.get(subject, _MOCK_ITEMS["math"])` — ключа `"russian"` в словаре нет, поэтому диагностика по русскому в mock-режиме тоже отдаёт вопросы по математике.
6. **Dashboard** — код реален, но входные данные сейчас всегда фиктивные из-за mock-диагностики.
7. **Practice (тренажёр)** — полностью реальный: 45 задач, детерминированный подбор темы, точная проверка ответа. Единственный полностью работающий обучающий контур продукта.
8. **Answer / Error** — тренажёр показывает верно/неверно и разбор ошибки — реально работает.
9. **AI Tutor** — история сообщений сохраняется реально, ответ ассистента — фиксированная строка-заглушка без RAG.
10. **Progress** — только через дашборд; отдельной истории/графика прогресса во времени нет.

## Мёртвые кнопки / несостыковки в коде

- **Logout на мобильных недоступен через сайдбар** — `components/Shell.tsx`, блок с email/«Выйти» имеет класс `hidden md:block`. На мобильном пользователь не может выйти из аккаунта через UI.
- **Refresh-токен выдаётся, но никогда не используется** — `login`/`register` возвращают `{access_token, refresh_token}`, фронтенд сохраняет только `access_token`. Через 60 минут доступ обрывается без переавторизации, включая посреди 45-минутной диагностики.
- **`/api/v1/diagnostics/answer` не блокирует ответы после `is_final`** — не критично, но отсутствует серверная защита от «лишних» ответов.
- Пустые/загрузочные состояния сделаны аккуратно везде, где ожидаются («Загрузка задания…», «Печатает…» и т.д.) — явных «сломанных» состояний в коде не найдено.

## Рекомендации

1. **Обновить Next.js** — минимум оценить патч в пределах 14.x, иначе спланировать миграцию на 16.x отдельной задачей с regression-тестированием. Приоритет HIGH — один из CVE это unauthenticated RCE.
2. **Завести `.eslintrc`** (`next/core-web-vitals`) — быстро, закрывает то, что линт фактически не запускался.
3. **Прогнать `docker compose up --build` целиком на реальной машине или в CI** перед следующим деплоем.
4. **Добавить CI** (GitHub Actions), который на каждый PR поднимает Postgres+Redis как сервисы и гоняет `pytest`, `npm run build`, `tsc --noEmit`, `npm audit --audit-level=high` — на 100 пользователях это не избыточно, это дешёвая страховка от регрессий (см. серию `Revert`-коммитов в git-истории).
5. Добавить минимальный ручной чек-лист регресса перед каждым релизом, пока нет автотестов фронтенда (см. `docs/qa/test-strategy.md`).
