# ИИ-репетитор — аудит и архитектура (Фаза 10)

## Текущее состояние: ИИ не существует в продукте

Это нужно сказать прямо, потому что от этого зависят все остальные разделы этого документа. В коде backend нет:
- ни одного вызова к LLM-провайдеру (YandexGPT, GigaChat, OpenAI, Anthropic — ничего);
- ни одной строчки эмбеддинг-логики или векторного поиска (`pgvector` установлен в образе БД, но не активирован ни одной миграцией);
- ни одного промпт-шаблона;
- ни одного модуля retrieval (поиска по базе знаний/учебникам/ФИПИ).

Вся «ИИ»-функциональность в `app/core/ai_client.py` — это заранее написанные строки/структуры, возвращаемые при `AI_SERVICE_MOCK=true` (значение по умолчанию), и HTTP-клиент к внешнему сервису, который по контракту (`docs/ai-service-contract.md`) должен существовать по адресу `AI_SERVICE_URL`, но нигде в известной инфраструктуре не задеплоен. Единственный реальный ML-артефакт в проекте — офлайн-эксперимент с моделью **Qwen2.5-3B-Instruct (4-bit квантизация)**: точность 88.3%, среднее время ответа **38.4 сек на CPU** при требовании ТЗ ≤5 сек, GPU не измерялся. Это эксперимент одного члена команды (Data Scientist), не интегрированный в работающий продукт.

## Аудит по чек-листу Фазы 10 (модель / промпты / контекст / память / RAG / эмбеддинги / векторная БД / грounding / галлюцинации / безопасность / prompt injection / латентность / стоимость / оценка)

Поскольку системы физически нет, аудит превращается в **набор требований к тому, что нужно спроектировать**, а не в оценку существующего:

- **Модель**: не выбрана окончательно. Питч-дек называет YandexGPT как целевую, офлайн-тест проводился на Qwen2.5-3B — это разные модели, выбор не финализирован. Для образовательного контента на русском языке и соответствия требованиям к персональным данным несовершеннолетних (152-ФЗ, локализация обработки) — российский провайдер (YandexGPT/GigaChat) логичнее иностранного API с точки зрения комплаенса, но у него своя стоимость/качество/латентность, которые не измерены в этом аудите (UNKNOWN).
- **Промпты**: не существуют. Нужно спроектировать с нуля под каждый из режимов ниже.
- **Контекст**: `docs/ai-service-contract.md` предусматривает передачу `history` (роль+текст) в чат и `previous_answers` в диагностику — это правильная основа, но контракт **не передаёт educational-контекст**, который CLAUDE.md явно требует сохранять («student, topic, skill, task, attempt, error, knowledge state and learning objective»): сейчас в запросе к ассистенту передаётся только `subject` (math/russian), без темы, без текущего Knowledge State ученика, без информации о том, над каким заданием/ошибкой он сейчас работает. Если ученик открывает ассистента прямо с экрана тренажёра после ошибки в конкретном задании, этот контекст **не долетает до ИИ** в текущем контракте — прямой разрыв между тем, что заявлено (персонализированный ИИ-репетитор) и тем, что технически возможно передать.
- **Память**: только история сообщений внутри одной `chat_session` — нет памяти между сессиями/предметами, нет использования Knowledge State ученика при генерации ответа.
- **RAG**: заявлено, не реализовано. Нет базы знаний (учебники/ФИПИ) ни в каком виде — ни сырых документов, ни чанков, ни эмбеддингов.
- **Эмбеддинги/векторная БД**: не реализовано; `pgvector` установлен, но простаивает.
- **Grounding/галлюцинации**: без RAG модель будет отвечать «из головы» — для математики это относительно безопасно (проверяемые факты), для методических рекомендаций/объяснений частей экзамена — риск давать методически неточные объяснения без привязки к актуальному кодификатору ФИПИ. Явного плана проверки фактической точности (eval-датасета помимо разового офлайн-теста на 88.3%) не обнаружено.
- **Безопасность/prompt injection**: сообщение ученика (`message`, `answer`) сейчас сохраняется как сырая строка и по контракту будет передано напрямую в промпт LLM без какой-либо санитизации/экранирования на уровне backend. Для образовательного продукта, используемого несовершеннолетними, риск не гипотетический: ученик технически может попытаться заставить модель уйти от темы предмета, сгенерировать неуместный контент, или (при появлении RAG) — через prompt injection в собственном вопросе повлиять на системный промпт. **Рекомендация**: как только AI-сервис подключается по-настоящему — задать на уровне контракта системный промпт с жёсткими границами роли («ты школьный репетитор по математике/русскому, отвечай только по теме»), плюс модерация выходного контента (хотя бы базовый content-filter), это не входит в объём текущего backend-репозитория (он лишь передаёт данные), но должно быть явным требованием к сервису Валентины при приёмке.
- **Латентность**: открытый вопрос уже зафиксирован в `docs/ai-service-contract.md` самим автором контракта — 38.4 сек офлайн-замер на CPU vs требование ≤5 сек, GPU не измерялся. Это прямой риск для синхронного HTTP-паттерна, который контракт описывает как основной сейчас.
- **Стоимость**: не оценивалась нигде в проектной документации в явных цифрах на пользователя/месяц — см. расчёт в `docs/business/financial-model-v2.md` (готовится параллельно), где закладывается консервативная оценка по токенам/запросам.
- **Оценка (evaluation)**: единственная существующая метрика — разовый офлайн-тест точности 88.3% на неизвестном по составу eval-наборе (детали методологии теста не задокументированы в репозитории). Нет continuous eval, нет golden-датасета вопросов ОГЭ с эталонными ответами для регрессионного тестирования качества после смены модели/промпта.

## Явное решение: RAG на MVP — обоснованно ли?

**Да, но не в объёме, заявленном в питч-деке, и не сразу.** Аргументация от первого принципа (CLAUDE.md, принцип 2 и 5):

- Задача «объяснить тему ОГЭ по математике/русскому "на пальцах"» для 9 класса — это конечная, хорошо документированная предметная область (кодификатор ФИПИ, ограниченное число тем — см. `oge-knowledge-graph.md`). Современные инструктированные LLM среднего размера уже неплохо справляются с этим без retrieval, особенно если промпт содержит структурированный контекст темы/навыка из уже спроектированной (но не реализованной) Skill Graph — то есть **можно получить 80% ценности через качественный system-prompt + структурированный контекст из своей БД, без единой строчки RAG-инфраструктуры**.
- RAG оправдан там, где нужна **привязка к конкретному источнику с указанием страницы/пункта критерия ФИПИ** (например, для проверки части 2 по официальным критериям оценивания, где точность формулировки критерия критична, или для избежания устаревших/неверных формулировок из "памяти" модели). Это уже не MVP-требование, а Launch-стадия.
- **Рекомендация**: на MVP — прямой вызов LLM с richly-структурированным промптом (тема, навык, уровень ученика, история диалога), без векторного поиска. Ввести RAG на Launch-стадии, когда появится реальная потребность в проверке части 2 по критериям ФИПИ и есть время подготовить корпус (учебники + кодификатор + критерии оценивания) — `pgvector` для этого объёма данных полностью достаточен, отдельный векторный движок (Pinecone/Weaviate/Qdrant) не нужен ни на одной из трёх стадий масштабирования, описанных в `02-target-architecture.md`.

## Режимы ИИ-репетитора (Фаза 10, требование)

Ниже — определение режимов для будущей реализации (ни один не существует сегодня):

| Режим | Назначение | Приоритет |
|---|---|---|
| **Explain (Объяснить)** | Развёрнутое объяснение темы/понятия «на пальцах» — базовый режим, отражённый в текущем UI чата | MVP |
| **Hint (Подсказка)** | Не давать готовый ответ, а подтолкнуть к следующему шагу решения — критично для тренажёра (сейчас там нет режима подсказки вообще, только «ответ верный/неверный + готовое объяснение постфактум») | MVP+ |
| **Socratic (Сократический)** | Задавать наводящие вопросы вместо прямых ответов — педагогически ценно, но сложнее в промпт-инжиниринге и легче ломается (модель может «сорваться» и просто дать ответ) — начинать после Explain/Hint | Launch |
| **Check Answer (Проверка ответа)** | Для развёрнутых ответов (часть 2) — формально самая заявленная в питч-деке фича и технически самая сложная (нужны эталонные критерии ФИПИ, структурированный вывод с баллами по критериям) | Launch, требует RAG |
| **Error Analysis (Разбор ошибки)** | Не общий разбор задания (как сейчас в тренажёре), а анализ *конкретной* ошибки, которую сделал ученик — требует передачи в промпт не только правильного ответа, но и того, что именно ответил ученик и в чём вероятная причина (например, характерная ошибка знака при переносе через равенство) | MVP+ |
| **Simplify (Упростить)** | Переформулировать объяснение проще/подробнее по запросу ученика («не понял, объясни проще») | MVP+ |
| **Exam Mode (Режим экзамена)** | Имитация условий экзамена — без подсказок, с таймером, с итоговой оценкой по критериям — самый требовательный к точности grounding режим | Scale |

## Режимы подробно: educational context и риски

Директива Фазы 10 требует для каждого режима явно определить его встраивание в образовательный контекст (student, topic, skill, task, attempt, error, knowledge state, learning objective — раздел AI, CLAUDE.md) и риски. Ни один из режимов ниже не реализован в коде — сегодня есть один недифференцированный чат (`axiom-frontend/app/assistant/page.tsx`, `axiom-backend/app/api/v1/assistant.py`), без переключателя режима и без передачи чего-либо, кроме `subject` и текста сообщения. Это прямое нарушение принципа CLAUDE.md «AXIOM is not a generic AI chat» — технически сегодня это ровно generic AI chat (пока что в виде заглушки).

### Explain (Объяснить)
- **Что и зачем**: развёрнутое объяснение понятия/темы по свободному вопросу ученика — базовый режим просветительского диалога, не привязанный к конкретному заданию.
- **Educational context**: student (класс, предмет), topic — в идеале ученик выбирает или система определяет тему из графа `oge-knowledge-graph.md`; skill/knowledge_state — чтобы объяснение было на уровне текущего владения (не объяснять квадратные уравнения языком для тех, кто ещё не освоил линейные); learning objective — «понять концепцию», не «решить конкретную задачу».
- **Риски**: галлюцинации на методических деталях (например, неточная формулировка правила ОГЭ) — без grounding через knowledge cards (см. решение по RAG выше) модель отвечает «из головы»; относительно низкий риск prompt injection (открытый вопрос, а не ответ ученика с потенциально «отравленным» текстом); риск утечки данных других учеников отсутствует при корректной изоляции сессии по `session_id`+`user_id` (см. `assistant.py` — подтверждено тестом `test_other_user_cannot_access_session`).

### Hint (Подсказка)
- **Что и зачем**: не готовый ответ, а следующий шаг/наводка — критично встроить прямо в тренажёр (сейчас там нет кнопки «подсказка» вообще — `axiom-frontend/app/trainer/page.tsx` не содержит такого элемента).
- **Educational context**: task (конкретное задание из `trainer_tasks`, включая `correct_answer`, который **не должен** попадать в промпт как «спойлер» дословно, а должен использоваться только для генерации частичной подсказки), attempt (сколько попыток уже сделано — при первой попытке подсказка мягче, при третьей — конкретнее), skill/topic.
- **Риски**: главный риск — модель «проговаривается» и выдаёт полный ответ вместо подсказки (нарушает педагогическую цель) — нужен либо строгий системный промпт с примерами отказа, либо (надёжнее на MVP) программная защита: подсказка генерируется из заранее подготовленного `explanation`/поднавыка (детерминированно, без LLM) на первом уровне, LLM подключается только для более гибкой второй подсказки. Утечка `correct_answer` в клиентский ответ — отдельный риск на уровне API-контракта, нужно валидировать, что ответ ассистента не содержит точного значения `correct_answer` (простая проверка на сервере перед отдачей клиенту).

### Socratic (Сократический)
- **Что и зачем**: наводящие вопросы вместо прямых ответов — самый педагогически ценный, но и самый хрупкий в промпт-инжиниринге режим.
- **Educational context**: task, attempt, error (если ученик уже ошибся — вопросы должны вести именно к месту ошибки, а не быть общими), knowledge_state (глубина наводящих вопросов зависит от уровня).
- **Риски**: модель может «сорваться» в прямой ответ при настойчивости ученика (классическая проблема инструктированных LLM) — требует regression-теста именно на этот сценарий («а если я 5 раз подряд попрошу ответ?») перед любым релизом этого режима; риск фрустрации ученика при слишком абстрактных вопросах без явной эскалации к более прямой подсказке после N неудачных попыток.

### Check Answer (Проверка ответа)
- **Что и зачем**: для заданий с развёрнутым ответом (часть 2 математики, сочинение/изложение русского) — оценка по критериям ФИПИ. Технически самый сложный режим (см. `docs/product/oge-knowledge-graph.md`, п.4 — точная проверка по критериям сейчас физически невозможна в архитектуре тренажёра, который проверяет только точным строковым сравнением, `answer_check.py`).
- **Educational context**: task (включая формальные критерии оценивания — которых сегодня нет в БД ни в каком виде, `trainer_tasks` не содержит структуры критериев), attempt (полный текст развёрнутого ответа ученика), learning objective (научиться формально правильно оформлять решение/сочинение, не только получить правильное число).
- **Риски**: самый высокий риск во всём документе — ложноположительная оценка («верно» при формально неполном решении) подрывает доверие сильнее отсутствия функции вообще (см. `docs/product/04-killer-feature.md`, кандидат 4: риск 2/5, самый низкий в таблице). Требует RAG/grounding на реальных критериях ФИПИ (см. решение по RAG — это единственный режим, для которого RAG оправдан не на MVP, а уже на Launch). Не включать в продакшн без человеческой проверки выборки оценок (human-in-the-loop) на старте.

### Error Analysis (Разбор ошибки)
- **Что и зачем**: не общий разбор задания (как сейчас статично показывается после любого ответа в тренажёре), а анализ именно того, что ответил ученик, и почему это может быть неверно — прямой аналог killer-feature кандидата 3 «Explain-my-mistake» (`04-killer-feature.md`, 23/30 баллов, второй приоритет после карты навыков).
- **Educational context**: task (вопрос + правильный ответ), attempt (конкретный ответ ученика, `submitted_answer` из `task_attempts`), error (не просто «неверно», а паттерн — при наличии — из графа ошибок `oge-knowledge-graph.md`, например «потеря знака при переносе»), skill/knowledge_state (для калибровки тона объяснения).
- **Риски**: узкий, структурированный вход (в отличие от свободного чата) — ниже риск галлюцинаций и prompt injection, поскольку большая часть промпта формируется backend'ом из проверенных данных, а не из свободного текста ученика; тем не менее `submitted_answer` — это ввод ученика и попадёт в промпт как есть, поэтому санитизация/лимит длины поля (сейчас `String(255)` без доп. валидации, см. `docs/architecture/03-database-design-v2.md`, п.3) остаётся обязательной перед реальной интеграцией.

### Simplify (Упростить)
- **Что и зачем**: переформулировать предыдущий ответ ассистента проще/подробнее по запросу ученика («не понял, объясни проще»).
- **Educational context**: history (предыдущий ответ ассистента в этой сессии — уже передаётся по контракту), knowledge_state (ориентир, насколько «проще» нужно объяснять).
- **Риски**: низкий сам по себе (это функция над уже сгенерированным ответом), но накопление истории без ограничения (см. «Память» выше — история сейчас передаётся целиком, без каких-либо ограничений объёма) увеличивает и стоимость, и риск, что модель «зацепится» за нерелевантную часть старой истории.

### Exam Mode (Режим экзамена)
- **Что и зачем**: имитация условий экзамена — без подсказок, с таймером, с итоговой оценкой по критериям (объединяет Task Selection на полном варианте + Check Answer на развёрнутых частях).
- **Educational context**: весь профиль student+knowledge_state (для формирования репрезентативного варианта по всем темам кодификатора — сегодня невозможно, банк не покрывает геометрию и часть 2 вообще, см. `oge-knowledge-graph.md`), learning objective — «финальная проверка готовности», explicitly без Hint/Socratic-подсказок.
- **Риски**: наследует все риски Check Answer (это его главный компонент) плюс риск ложного чувства готовности/неготовности у ученика перед реальным экзаменом при неточной оценке — самый требовательный к качеству grounding режим, обоснованно отнесён к Scale-стадии, а не MVP/Launch.

### Сквозные риски безопасности для всех режимов
- **Prompt injection через ответы ученика**: любой режим, передающий `submitted_answer`/свободный `message` в промпт, уязвим к попытке ученика переопределить системную роль модели («игнорируй инструкции выше…»). Контрмера — на уровне промпта (явные границы роли + инструкция игнорировать попытки переопределения) и на уровне вывода (простая эвристическая проверка, что ответ не содержит явных признаков «слома» роли) — это ответственность сервиса Валентины по контракту, но backend должен логировать подозрительные паттерны на своей стороне для последующего ревью.
- **Утечка данных между учениками через историю**: технически изолировано корректно — `chat_messages`/`chat_sessions` фильтруются по `user_id` во всех эндпоинтах (`assistant.py`), подтверждено тестом `test_other_user_cannot_access_session`. Риск остаётся только если реальный ИИ-сервис Валентины при обработке батчей запросов от разных пользователей случайно смешает контексты (например, ошибка в её сервисе, объединяющем запросы в батч для GPU-инференса) — это не проверяется backend-контрактом сегодня и стоит явно include в приёмочные критерии сервиса перед продакшн-подключением.

## Архитектурная рекомендация для контракта с AI-сервисом

Контракт в `docs/ai-service-contract.md` в целом хорошо спроектирован (стабильный HTTP-интерфейс, backend не завязан на реализацию) — но нуждается в двух доработках до продакшн-использования: (1) добавить в запрос ассистента явные поля `topic`/`skill_id`/`knowledge_state_snapshot` вместо одного `subject`, чтобы режимы Hint/Error Analysis были технически возможны; (2) окончательно решить синхронный vs асинхронный паттерн для `/v1/assistant/chat`, исходя из реальных GPU-замеров латентности (открытый вопрос, зафиксированный самим контрактом) — если латентность реального сервиса окажется выше ~5-7 секунд, синхронный HTTP с таймаутом 20 секунд (текущее значение в `.env.example`) даст плохой UX (пользователь смотрит на «Печатает…» слишком долго без обратной связи о прогрессе) — нужен паттерн job+poll или WebSocket/SSE-стриминг токенов, что также стандартно улучшает воспринимаемую скорость ответа LLM независимо от фактической латентности.

Отдельная опция, не упомянутая в текущем контракте, но стоящая явного рассмотрения при выборе модели: **хостed API вместо самостоятельного хостинга Qwen на CPU/GPU**. При 100 пользователях и объёме запросов, реалистичном для MVP, стоимость вызовов к managed-API (YandexGPT API, GigaChat API) может быть ниже, чем стоимость и инженерные усилия по поддержке собственной GPU-инференс-инфраструктуры ради латентности — а managed-API почти наверняка укладывается в ≤5 сек без дополнительной инженерии на стороне AXIOM. Это прямое применение принципа CLAUDE.md «не вводить сложность без реальной причины на текущем масштабе»: self-hosted LLM оправдан операционно (стоимость на токен ниже при большом объёме, контроль данных), но при 100 пользователях объём токенов, вероятно, слишком мал, чтобы окупить инженерные усилия по самостоятельному инференсу — решение по факту принадлежит Data Scientist команды (Валентина) и должно быть explicit trade-off, а не побочный эффект того, что офлайн-эксперимент проводился на локально запущенной модели.
