# Адаптивный движок обучения (Фаза 9)

> Контур: Student Model → Knowledge State → Skill Graph → Recommendation Engine → Task Selection → Attempt → Error Analysis → Knowledge Update → Next Recommendation. Ниже — что из этого контура есть сегодня, и что нужно на каждой стадии, **без преждевременного ML** (CLAUDE.md, принцип 5: «Prefer deterministic/rule-based solutions on MVP when sufficient»).

## Текущее состояние по звеньям контура

| Звено | Есть сегодня? | Как реализовано |
|---|---|---|
| Student Model | Частично | Только `users.grade` (класс) — ни одного поля про уровень/цели/дедлайн экзамена |
| Knowledge State | Фиктивно | `diagnostic_results` — правильная таблица по форме, но заполняется **захардкоженными значениями**, не зависящими от реальных ответов (см. `docs/audit/04-documentation-gap-analysis.md`) |
| Skill Graph | Отсутствует | Темы — плоские строки без иерархии, пререквизитов, связи между диагностикой и тренажёром (см. `database-design-v2.md`) |
| Recommendation Engine | Минимальная, но реальная | `dashboard.py: get_recommendations()` — темы, помеченные `weak=True` в последней диагностике, становятся рекомендациями. Логика верная, но входные данные сейчас фиктивны |
| Task Selection | Реальная, детерминированная | `trainer.py: _pick_topic()` — непройденные темы → тема с наименьшей долей верных ответов. Не использует Knowledge State/диагностику (явный TODO в коде) |
| Attempt | Реальная | `task_attempts` — полноценно пишется, с привязкой user+task+ответ+результат |
| Error Analysis | Минимальная | Только статичный текст объяснения, привязанный к заданию, не к конкретной ошибке ученика (нет анализа *какую именно* ошибку сделал — просто показывается общий разбор задания) |
| Knowledge Update | Отсутствует персистентно | Нет пересчёта состояния знаний после каждой попытки — `task_attempts` копится, но ничего не агрегирует их в обновлённую оценку владения темой вне рамок одной диагностической сессии |
| Next Recommendation | Частичная | Как в Recommendation Engine — зависит от актуальности Knowledge State, которого пока нет |

**Итог**: контур «нарисован» правильно на уровне архитектуры БД и API (это хороший знак — форма готова), но два ключевых звена (Knowledge State, Knowledge Update) сейчас не работают по существу, потому что вся диагностика — заглушка, а тренажёр не подключён к диагностике даже когда она заработает по-настоящему.

## Дизайн по стадиям (явно разделяя MVP / Launch / Advanced)

### MVP (сейчас — до реального ИИ-сервиса)

Ничего из этого не требует ML — только исправление уже спроектированных, но не соединённых частей:

1. **Соединить тренажёр с `diagnostic_results`** — при выборе следующего задания (`_pick_topic`) добавить приоритет темам, помеченным `weak=True` в последней диагностике, поверх существующей эвристики по истории тренажёра (сам код уже содержит TODO именно об этом — это готовая, недорогая задача).
2. **Ввести персистентный Knowledge State как простую формулу**, не ML: после каждой попытки в тренажёре обновлять `ability_score` темы как скользящее среднее (например, экспоненциально взвешенное: `new = old*0.8 + result*0.2`) в новой таблице `knowledge_state` (см. `database-design-v2.md`, Стадия 2 — можно и раньше, это дёшево). Это уже даёт «настоящую» адаптивность без единой строчки ML-кода — ровно в духе принципа 5 CLAUDE.md.
3. **Как только реальный ИИ-сервис заработает** — его CAT/IRT-оценка должна писаться в тот же `knowledge_state`, а не в отдельный изолированный контур, чтобы тренажёр и диагностика говорили на одном языке состояния ученика.

### Launch (коммерческий запуск, Стадия 2 архитектуры)

- **Skill Graph как явная таблица** (`skills`, `skill_prerequisites`) — уже сейчас есть первый черновой граф в `docs/product/oge-knowledge-graph.md` (готовится параллельно), его нужно перенести в БД.
- **Recommendation Engine с учётом пререквизитов**: не просто «слабая тема → рекомендация», а «слабая тема, у которой пререквизиты уже освоены → в приоритет; слабая тема без освоенных пререквизитов → сначала пререквизит». Это по-прежнему детерминированное правило (граф + топологический порядок), не ML.
- **Многофакторный Task Selection**: тема (слабость) × сложность (постепенное повышение при серии верных ответов, понижение при серии ошибок — простой алгоритм наподобие ELO/лестницы сложности, не требует нейросети) × давность последней практики темы (spaced repetition — можно взять готовый алгоритм типа SM-2, это не «ML», а формула).

### Advanced / Scale (Стадия 3, только если данных достаточно и есть измеримая гипотеза, что классические методы упёрлись в потолок)

- Полноценный Bayesian Knowledge Tracing или Deep Knowledge Tracing — **только если** накоплен достаточный объём попыток (по грубой оценке — от нескольких тысяч попыток на пользователя в базе, что при 100–1000 пользователях появится не сразу) и если A/B-тест показывает, что детерминированные правила Launch-стадии реально ограничивают retention/успеваемость. Здесь прямо применим принцип CLAUDE.md: «Do not build features merely because they are technically interesting» — питч-дек заявляет DKT сразу на MVP, но при текущем объёме данных (0 реальных пользователей на момент аудита) обучить содержательную DKT-модель физически не на чем.
- RL-планировщик подготовки (из питч-дека) — та же логика: RL требует симулятора или огромного объёма логов взаимодействия для сходимости; для расписания «что учить сегодня с учётом дедлайна и пробелов» на этом масштабе полностью достаточно детерминированного планировщика (жадный алгоритм по приоритету слабых тем с учётом дней до экзамена) — RL здесь не даёт измеримого преимущества при таком объёме данных и сильно увеличивает сложность/риск непредсказуемого поведения для образовательного продукта, где ошибка планировщика напрямую бьёт по ребёнку перед экзаменом.

## Итоговая рекомендация

Не пытаться реализовать «ИИ-адаптивность» одним большим прыжком к DKT/CAT/RL, как обещает питч-дек. Правильная последовательность — снизу вверх: (1) реально соединить уже существующие таблицы простой формулой обновления состояния знаний, (2) добавить граф пререквизитов как данные, а не как модель, (3) только на объёме данных, оправдывающем это, переходить к статистическим/ML-методам (IRT — с достаточным банком заданий и откликов, DKT — с достаточным логом попыток). Это прямое применение принципов 1, 2 и 5 из CLAUDE.md и одновременно самый быстрый путь к «работающей адаптивности» для демонстрации инвестору/жюри — без ожидания готовности внешнего ИИ-сервиса.

## Сводная таблица: звено конвейера × стадия

| Звено конвейера | MVP (сейчас) | Launch | Advanced/Scale |
|---|---|---|---|
| Student Model | `users.grade` + факт регистрации | + дата экзамена, цель (например, целевой балл) как явные поля профиля | Сегментация профилей по поведенческим кластерам — оправдано только при объёме пользователей, достаточном для устойчивой кластеризации (не Стадия 1/2) |
| Knowledge State | `knowledge_state` — EWMA-формула по попыткам тренажёра (без ML) | + реальная IRT-оценка от ИИ-сервиса, пишется в ту же таблицу | Bayesian/Deep Knowledge Tracing — см. критическую оценку ниже |
| Skill Graph | Плоские `topics` (строки → нормализованная таблица) | `skills`/`skill_prerequisites` из `oge-knowledge-graph.md`, перенесённые в БД | Автоматическое уточнение графа по данным о переносе ошибок между навыками — не раньше содержательного объёма логов |
| Recommendation Engine | `weak=True` из диагностики → приоритет в `_pick_topic` | + топологический порядок по пререквизитам | Персонализация по кластерам/RL — не оправдано на реалистичном для AXIOM объёме данных (см. ниже) |
| Task Selection | Случайный выбор среди нерешённых задач темы | + лестница сложности (ELO-подобная), + spaced repetition (SM-2-подобная формула) | Адаптивный подбор по калиброванным IRT-параметрам сложности задания (требует банка заданий на порядок больше 45) |
| Attempt | `task_attempts` — уже полноценно | Без изменений по существу, добавить тайминг попытки (время решения) как сигнал | — |
| Error Analysis | Статичное объяснение, привязанное к заданию | Классификация типа ошибки по паттерну (правило: «неверный знак», «потерян корень» и т.п. — размечается вручную по `oge-knowledge-graph.md`) | Автоматическая кластеризация паттернов ошибок по всем ученикам — требует содержательного объёма данных |
| Knowledge Update | EWMA после каждой попытки тренажёра | + вход от реальной диагностики, + учёт давности (decay) | Байесовское обновление с учётом неопределённости оценки |
| Next Recommendation | Простая функция от Knowledge State | + пререквизиты + сложность + davность практики | Полноценная оптимизация траектории (RL) — не оправдано, см. ниже |
