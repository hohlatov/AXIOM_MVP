# 04 — API: аудит as-is и предложения (Фаза 16)

> Аудит проведён: 2026-09-11. Источник — построчное чтение всех 5 роутеров (`axiom-backend/app/api/v1/*.py`), всех Pydantic-схем (`app/schemas/*.py`), `app/main.py`, `app/core/rate_limit.py`, `app/core/security.py`. Сверено с живой OpenAPI-схемой прод-бэкенда (`https://axiombackend.relaxdev.ru/openapi.json`, зафиксировано в `docs/audit/03-live-vs-code.md`) — состав эндпоинтов совпадает 1:1 с кодом.

## 1. Общие параметры API

- **Базовый URL**: `/api/v1` для всех бизнес-роутеров; `GET /health` — единственное исключение, живёт вне префикса (`app/main.py:32-34`) — непоследовательно, но не критично (health-check действительно часто держат вне версионирования).
- **Версионирование**: единственный механизм — статический префикс пути `/api/v1`. Нет заголовка версии, нет content negotiation, нет задокументированной политики депрекации endpoint'ов. Для одного клиента (собственный frontend) и 100 пользователей это осознанно достаточно; для публичного API (партнёры/B2B, Stage 2+) потребуется явная политика.
- **Аутентификация**: `Authorization: Bearer <JWT access-токен>`, реализовано через `OAuth2PasswordBearer(tokenUrl="/api/v1/auth/login")` (`auth.py:35`) — стандартная FastAPI-зависимость `get_current_user` (`auth.py:85-97`), используется во всех защищённых роутерах путём прямого импорта функции из `auth.py` (не отдельного auth-сервиса — оправдано для монолита).
- **Access-токен**: HS256 JWT, TTL 60 минут (`access_token_expire_minutes=60`), payload `{sub, type: "access", iat, exp}`.
- **Refresh-токен**: выдаётся (TTL 30 дней), но **в API нет ни одного эндпоинта, который бы его принимал** — `/auth/refresh` не существует. Токен генерируется и отдаётся клиенту вникуда (см. `docs/architecture/03-database-design-v2.md`, раздел 4). Frontend его тоже не использует (`lib/auth.tsx` сохраняет только `access_token`) — то есть это несогласованность и на бэкенде, и на фронтенде одновременно, не только «фронт не дотянул».
- **Формат ошибок — НЕ единый**:
  - Бизнес-ошибки (`HTTPException`) → `{"detail": "человекочитаемая строка на русском"}`, например `{"detail": "Email уже зарегистрирован"}`.
  - Ошибки валидации Pydantic (422) → дефолтный формат FastAPI: `{"detail": [{"loc": [...], "msg": "...", "type": "..."}]}` — **массив объектов**, не строка.
  - Клиенту нужно разбирать два разных типа значения в одном и том же поле `detail` в зависимости от статус-кода. Фронтенд (`lib/api.ts:29-37`) обходит это грубо: `if (body?.detail) detail = body.detail`, что при 422 присвоит `detail` переменной **массив**, а не строку, и то, что дальше показывается пользователю (например, через `error.message`), скорее всего отрендерится как `[object Object]` либо `"[object Object],[object Object]"` в UI, а не осмысленный текст. Это стоит проверить отдельным ручным тестом формы регистрации с заведомо невалидными данными.
  - Нет машинно-читаемого кода ошибки (`error_code`), нет `request_id`/`trace_id` в ответе — при обращении в поддержку невозможно сослаться на конкретный инцидент без сверки таймстемпа.
- **CORS**: один разрешённый origin — `settings.frontend_url`, `allow_credentials=True`, методы/заголовки — wildcard (`main.py:17-23`). Корректно для единственного known frontend.
- **Пагинация**: **отсутствует полностью** — ни один эндпоинт, возвращающий список (`GET /assistant/sessions/{id}/history`, косвенно `GET /dashboard/summary` со списками `progress`/`recommendations`), не принимает `limit`/`offset`/курсор. Для истории чата с ИИ-репетитором — растущий без ограничения список при каждом открытии — см. `03-database-design-v2.md`, раздел 1.8.
- **Идемпотентность**: не реализована ни для одного POST-эндпоинта (нет `Idempotency-Key`). Практическое следствие — `POST /trainer/submit` при повторной отправке (двойной клик, retry сети) создаст вторую строку `task_attempts` для того же задания; не искажает корректность проверки ответа, но искажает статистику попыток, на которой строится подбор следующей темы (`trainer.py:36-46`).
- **Health-check**: `GET /health` без аутентификации, без rate limit, возвращает статичный `{"status": "ok"}` — не проверяет реальную доступность БД/Redis/ИИ-сервиса (поверхностный health-check, не readiness-check).

## 2. Rate limiting — сводно

Реализация: Redis fixed-window (`app/core/rate_limit.py`), два режима — по IP (`rate_limit_by_ip`, FastAPI-зависимость) и по произвольному ключу (`rate_limit_by_key`, вызывается вручную внутри тела эндпоинта — используется для лимита по email, независимо от IP).

**Известный нерешённый риск** — прямо зафиксирован как TODO в самом коде (`rate_limit.py:14-18`): `request.client.host` за обратным прокси (RelaxDev на проде) — это адрес прокси, а не реального клиента, если `X-Forwarded-For` не проброшен и не обрабатывается явно. Это значит, что **всё троттлинг по IP на проде прямо сейчас, вероятно, лимитирует один и тот же псевдо-IP для всех пользователей разом** (общий счётчик на IP прокси) либо не работает вовсе, в зависимости от того, что реально приходит в `request.client.host` через слой RelaxDev. Это не проверено динамически в рамках этого аудита (нужен запрос с прод-окружения), но статически код на это указывает однозначно. См. также `docs/architecture/technical-debt.md`.

**Ключевая находка**: rate limiting есть только на пре-аутентификационных эндпоинтах (защита от брутфорса/спама регистраций — сделано аккуратно и по делу). **Ни один аутентифицированный бизнес-эндпоинт не ограничен по частоте**, включая `POST /assistant/chat` — прямую точку интеграции с платным LLM-сервисом. Сейчас это не стоит денег (мок), но это ровно тот компонент, который начнёт стоить денег в первую очередь, как только сервис Валентины будет задеплоен (`AI_SERVICE_MOCK=false`). Один авторизованный пользователь (или скомпрометированный токен) сможет отправлять неограниченное количество запросов к LLM без какого-либо контроля стоимости на уровне API. Это должно быть закрыто **до**, а не после первого реального подключения ИИ-сервиса — см. приоритет CRITICAL/HIGH в `technical-debt.md`.

## 3. Эндпоинты — детальный аудит

### 3.1 Auth (`app/api/v1/auth.py`)

#### `POST /api/v1/auth/register`
- Auth: нет. Rate limit: 5/час по IP.
- Запрос (`UserRegister`): `email: EmailStr`, `password: str (min_length=8)`, `grade: int | None`, `parental_consent: bool` (обязателен `true` — валидатор `consent_must_be_given` отклоняет `false` уже на уровне Pydantic, до обращения к БД — реализовано хорошо, 152-ФЗ согласие проверяется до записи).
- Ответ: `201` → `UserOut {id, email, grade, parental_consent_given}`.
- Ошибки: `409` email уже занят (см. риск гонки в разделе 1 / `03-database-design-v2.md`), `422` валидация Pydantic.
- Замечание: пароль не имеет верхней проверки сложности (только `min_length=8`) — для 100 пользователей приемлемо, для будущего роста стоит хотя бы проверить на самые популярные пароли (`HaveIBeenPwned`-подобный список) — не блокер MVP.

#### `POST /api/v1/auth/login`
- Auth: нет. Rate limit: 8/15мин по IP + 5/15мин по email.
- Запрос (`UserLogin`): `email`, `password`.
- Ответ: `200` → `TokenPair {access_token, refresh_token, token_type: "bearer"}`.
- Ошибки: `401` неверный email/пароль (единое сообщение — не раскрывает, что именно неверно, корректно против user enumeration), `429` при превышении лимита с заголовком `Retry-After`.
- Замечание: ответ не содержит данные пользователя — фронтенду нужен отдельный вызов `GET /auth/me`, то есть два round-trip'а для полного логина. Не критично, но можно было бы отдавать `UserOut` вместе с токенами одним ответом.

#### `GET /api/v1/auth/me`
- Auth: обязательна. Rate limit: нет.
- Ответ: `200` → `UserOut`.
- Ошибки: `401` невалидный/просроченный токен.

#### `GET /api/v1/auth/vk/login`
- Auth: нет. Rate limit: нет (не нужен — эндпоинт не обращается ни к БД, ни к внешнему сервису, только генерирует `state` и собирает URL).
- Ответ: `200` → `{authorize_url, state}`.
- Замечание: `state` возвращается в теле ответа, а не сохраняется на сервере (в Redis/сессии) для последующей сверки при callback. Классическая защита от CSRF в OAuth-потоке через `state` подразумевает, что сервер сам его помнит и сверяет при возврате — здесь этого нет: `vk_callback` вообще не принимает и не проверяет `state`. Это ослабляет защиту OAuth-потока от CSRF/подмены callback. Подробнее — зона ответственности `docs/security/security-audit.md`, здесь фиксируется как API-контрактный пробел (state генерируется, но никогда не валидируется).

#### `GET /api/v1/auth/vk/callback`
- Auth: нет. Rate limit: 20/час по IP.
- Query-параметры: `code: str` (обязателен), `parental_consent: bool` (**обязателен без default** — FastAPI требует его в каждом запросе, включая вход **уже существующего** пользователя, для которого согласие уже давно дано и хранится в БД). Это лишнее трение в контракте: пере-логинящийся пользователь вынужден заново передавать `parental_consent`, даже если бэкенд его в этом случае полностью игнорирует (используется только в ветке создания нового аккаунта, `auth.py:134-144`).
- Ответ: `200` → `TokenPair`.
- Ошибки: `400` ошибка обмена кода на токен VK, `422` если это новый аккаунт и `parental_consent=false`.
- Замечание по HTTP-семантике: `GET`-запрос с побочным эффектом (может создать нового пользователя в БД) — не идемпотентен, что противоречит семантике GET, хотя прагматично объяснимо стандартным OAuth redirect-flow (VK сам делает GET-редирект с `code` в query). Общепринятая практика для таких колбэков.

#### `POST /api/v1/auth/password-reset/request`
- Auth: нет. Rate limit: 5/час по IP + 3/час по email.
- Запрос: `{email}`. Ответ: `202` всегда одинаковый `{"detail": "Если email зарегистрирован..."}` независимо от того, существует ли email — корректная защита от user enumeration (`auth.py:168-176`, явно прокомментировано в коде).
- Токен сброса — `secrets.token_urlsafe(32)`, хранится в Redis с TTL 30 минут, одноразовый (`redis.delete` после использования).

#### `POST /api/v1/auth/password-reset/confirm`
- Auth: нет. Rate limit: 15/час по IP.
- Запрос: `{token, new_password (min 8)}`. Ответ: `200`.
- Ошибки: `400` невалидный/истёкший токен.
- Замечание: 15/час по IP на confirm выглядит великодушно по сравнению с 3/час по email на request — но токен сам по себе high-entropy (32 байта url-safe), так что подбор токена перебором в разумное время невозможен независимо от лимита; лимит здесь скорее защищает Redis/БД от шума, чем от реальной атаки полным перебором.

### 3.2 Dashboard (`app/api/v1/dashboard.py`)

#### `GET /api/v1/dashboard/summary`
- Auth: обязательна. Rate limit: нет.
- Ответ: `200` → `DashboardSummary {grade, progress: [SubjectProgress], recommendations: [Recommendation], quick_actions: [str], has_diagnostic_result: bool}`.
- Логика: `progress` и `recommendations` вычисляются "на лету" из последней **завершённой** `DiagnosticSession` по каждому предмету (`_latest_completed_session`, `dashboard.py:25-32`) — два независимых предмета жёстко захардкожены в `SUBJECT_LABELS = {"math": "Математика", "russian": "Русский язык"}` (`dashboard.py:22`), не читаются из БД/справочника.
- Замечание: данные тренажёра (`task_attempts`) **никак не влияют** на `progress`/`recommendations` — явный `TODO` в самом файле (`dashboard.py:7-8`): "подмешать сюда статистику тренажёра... когда накопится достаточно данных". То есть дашборд полностью зависит от диагностики, а диагностика сейчас — мок с фиксированным результатом (см. `docs/audit/02-runtime-audit.md`) — практическое следствие: прогресс на дашборде у всех пользователей идентичен и не отражает реальную работу в тренажёре.

### 3.3 Diagnostics (`app/api/v1/diagnostics.py`)

Все 4 эндпоинта — тонкая обвязка вокруг `app/core/ai_client.py` (см. отдельно раздел 4).

#### `POST /api/v1/diagnostics/start?subject={math|russian}`
- Auth: обязательна. Rate limit: **нет**.
- Query: `subject` — валидируется regex `^(math|russian)$` прямо в сигнатуре FastAPI (`Query(pattern=...)`) — аккуратно, ошибка формата вернёт `422` до создания сессии.
- Создаёт `DiagnosticSession(status="in_progress")`, затем вызывает `get_next_item(...)`.
- Ответ: `201` → `StartDiagnosticOut {session_id, item: DiagnosticItem}`.
- Ошибки: `503` если `AIServiceError` (ИИ-сервис недоступен/таймаут) — **сессия в БД уже создана и закоммичена до вызова ИИ-сервиса** (`diagnostics.py:36-44`: `db.commit()` на строке 38, вызов `get_next_item` на строке 42), то есть при сбое ИИ-сервиса в БД остаётся "осиротевшая" сессия `in_progress` без единого вопроса — не проблема целостности данных, но накопление мусорных сессий при нестабильном ИИ-сервисе.

#### `POST /api/v1/diagnostics/answer`
- Auth: обязательна. Rate limit: **нет**.
- Запрос (`AnswerIn`): `{session_id, item_id, answer}`.
- Проверки: сессия существует и принадлежит пользователю (`404` иначе), сессия `in_progress` (`409` если уже завершена) — хорошо реализованная защита от подмены чужой сессии.
- **Находка**: нет проверки, что `item_id` соответствует **последнему выданному** вопросу этой сессии — можно отправить ответ на произвольный `item_id`, включая уже отвеченный ранее (см. также `03-database-design-v2.md`, раздел 1.3 — нет UNIQUE(`session_id`, `item_id`)). Также, как зафиксировано в `docs/audit/02-runtime-audit.md`, нет проверки на отправку ответа после того, как сервис уже вернул `is_final=true`.
- Ответ: `200` → `StartDiagnosticOut` со следующим вопросом (или `is_final=true`).

#### `POST /api/v1/diagnostics/{session_id}/finalize`
- Auth: обязательна (+ проверка владения сессией). Rate limit: **нет**.
- Идемпотентно по факту: если `session.status == "completed"`, просто возвращает уже сохранённый результат повторно, не дёргая ИИ-сервис заново (`diagnostics.py:84-85`) — хорошее решение, защищает от двойной записи `DiagnosticResult` при повторном вызове.
- Ответ: `200` → `DiagnosticResultOut {status, topics: [TopicResult]}`.
- Ошибки: `503` при сбое ИИ-сервиса.

#### `GET /api/v1/diagnostics/{session_id}/result`
- Auth: обязательна (+ владение). Rate limit: **нет**.
- Ответ: `200` → `DiagnosticResultOut`. Не проверяет, что сессия уже `completed` — для `in_progress` сессии просто вернёт пустой `topics: []`, без явного признака "результат ещё не готов" в контракте ответа (клиенту приходится по смыслу самому понимать, что пустой список = либо "не завершена", либо "завершена без findings" — эти два состояния неразличимы в ответе).

### 3.4 Trainer (`app/api/v1/trainer.py`)

#### `GET /api/v1/trainer/next-task?subject={math|russian}`
- Auth: обязательна. Rate limit: **нет**.
- Логика подбора темы (`_pick_topic`, `trainer.py:27-61`) — полностью детерминированная, без ИИ: приоритет темам, которые пользователь ещё не пробовал (`random.choice` среди непройденных тем), иначе — тема с наименьшей долей верных ответов. Внутри темы — предпочтение задачам, которые пользователь ещё не решил верно. Это ровно то, что рекомендует CLAUDE.md («предпочитать детерминированные решения на MVP») — реализовано корректно и по существу.
- Ответ: `200` → `TrainerTaskOut` (**без** `correct_answer`/`explanation` — правильно скрыты до ответа, `trainer.py schemas:6-16`).
- Ошибки: `404` если для предмета вообще нет заданий в БД (например, до запуска `seed_tasks.py`).

#### `POST /api/v1/trainer/submit`
- Auth: обязательна. Rate limit: **нет**.
- Запрос (`SubmitAnswer`): `{task_id, answer (1-255 симв.)}`.
- Проверка ответа — `answers_match()` (`app/core/answer_check.py`) — точное строковое сравнение после нормализации (убрать пробелы, привести к нижнему регистру, унифицировать `,`→`.`, нормализовать числовой формат через `%g`). Это осознанно простое решение (детерминированное, не ML), корректно для заданий с коротким числовым/буквенным ответом; не подойдёт для заданий с развёрнутым ответом (сочинение, доказательство) — таких заданий в текущем банке (`seed_tasks.py`) нет вообще, все 45 — с коротким проверяемым ответом.
- Ответ: `200` → `SubmitResult {is_correct, correct_answer, explanation}` — правильный ответ и разбор отдаются сразу после отправки, независимо от результата — хорошо для обучающего цикла (немедленная обратная связь).
- Ошибки: `404` если `task_id` не существует.
- Замечание: нет проверки, что `task_id` относится к теме/предмету, который вообще выдавался этому пользователю через `next-task` — можно отправить ответ на любой существующий `task_id` напрямую. Для MVP не критично (нет ставок/начисления баллов, влияющих на что-то ценное), но стоит иметь в виду при появлении геймификации/рейтингов.

### 3.5 Assistant (`app/api/v1/assistant.py`)

#### `POST /api/v1/assistant/chat`
- Auth: обязательна. Rate limit: **нет** (см. раздел 2 — главный риск API).
- Запрос (`ChatRequest`): `{session_id: UUID | null, subject: str | null, message: str}`. Если `session_id` не передан — создаётся новая `ChatSession`, для чего `subject` становится обязательным (проверка в коде, `assistant.py:34-38`, не на уровне Pydantic-схемы — оба поля формально `Optional` в схеме, реальная обязательность появляется только в runtime-логике; в OpenAPI-схеме это не будет видно как условно обязательное поле, что может путать интеграторов, читающих только Swagger).
- Логика: загружает всю историю сообщений сессии, добавляет новое сообщение пользователя, коммитит, вызывает `get_chat_answer(...)`, сохраняет ответ ассистента. Два отдельных `db.commit()` (строки 53 и 62) — если `get_chat_answer` упадёт между ними (503), сообщение пользователя **уже сохранено** в БД, а ответа ассистента не будет — при следующем открытии истории пользователь увидит своё сообщение "в воздухе" без ответа. Не критично для целостности, но UX-момент стоит проверить на фронтенде (обрабатывается ли 503 явным "не удалось получить ответ, попробуйте ещё раз" без потери введённого текста).
- Ответ: `200` → `ChatResponse {session_id, answer, sources: [str]}`. `sources` — задел под RAG-цитирование источников, сейчас всегда `[]` (мок не возвращает источники, `ai_client.py:72-77`).
- Ошибки: `404` чужая/несуществующая сессия, `422` новая сессия без `subject`, `503` сбой ИИ-сервиса.
- **Важно**: `AI_SERVICE_TIMEOUT_SECONDS=20` (`.env.example`), но офлайн-замер реальной модели (Qwen2.5-3B-Instruct 4-bit, CPU) дал **среднюю задержку 38.4 сек** — то есть текущий таймаут заведомо меньше наблюдаемой задержки реальной модели почти в 2 раза. Если сервис Валентины будет подключён с текущими настройками и близкой производительностью (CPU-инференс), **большинство запросов к `/assistant/chat` и `/diagnostics/*` будут завершаться `503` по таймауту `httpx`**, а не успешным ответом. Это прямое противоречие между конфигурацией по умолчанию и уже собранными эмпирическими данными, зафиксированными в самом `docs/ai-service-contract.md` как открытый вопрос. Синхронная модель `httpx.post(...).raise_for_status()` (`ai_client.py:41-47, 59-64, 80-85`) с фиксированным HTTP-таймаутом не переживёт такую задержку без изменения на асинхронный паттерн job/poll — что контракт сам предлагает как возможное решение, но пока не выбрано.

#### `GET /api/v1/assistant/sessions/{session_id}/history`
- Auth: обязательна (+ владение). Rate limit: **нет**.
- Ответ: `200` → `list[ChatMessageOut {role, content, created_at}]`, без пагинации (см. раздел 1).

## 4. Внутренний контракт с ИИ-сервисом (не публичный API, но часть общей API-поверхности системы)

`app/core/ai_client.py` — единственная точка интеграции. Три функции, каждая — либо мок, либо `httpx.AsyncClient` POST-запрос:
- `get_next_item` → `POST {AI_SERVICE_URL}/v1/diagnostics/next-item`
- `finalize_session` → `POST {AI_SERVICE_URL}/v1/diagnostics/finalize`
- `get_chat_answer` → `POST {AI_SERVICE_URL}/v1/assistant/chat`

Обработка ошибок унифицирована: любой `httpx.HTTPError` → `AIServiceError` → HTTP `503` наружу. Это хороший, простой паттерн для MVP — нет ретраев, нет circuit breaker, нет фолбэка на кэш/дефолтные данные при недоступности сервиса — что осознанно допустимо на 100 пользователях (усложнение ради устойчивости, которой пока не требует нагрузка), но обязательно к пересмотру на Stage 2 при реальном SLA перед платящими пользователями.

Баг мок-режима (уже зафиксирован в `docs/audit/02-runtime-audit.md`, здесь — как API-контрактная находка): `_MOCK_ITEMS.get(subject, _MOCK_ITEMS["math"])` (`ai_client.py:33`) — словарь `_MOCK_ITEMS` содержит только ключ `"math"`, ключа `"russian"` нет вовсе. Любой вызов `GET /diagnostics/start?subject=russian` в мок-режиме молча (без ошибки) отдаёт вопросы **по математике**. Контракт API формально не нарушен (ответ валиден по схеме), но семантически это баг, который скроет реальное поведение диагностики по русскому языку от любого, кто тестирует продукт только через API/UI, не читая код.

## 5. Что отсутствует и понадобится (не сейчас — по мере достижения триггеров Stage 2/3, см. `02-target-architecture.md`)

- `POST /api/v1/auth/refresh` — обменять refresh-токен на новый access-токен (сейчас токен выдаётся, но нигде не принимается — см. раздел 1).
- `POST /api/v1/auth/logout` (либо просто отзыв на стороне клиента, если явно решено не вводить server-side revocation для MVP — сейчас это неявное решение по умолчанию, а не осознанный выбор, задокументированный где-либо).
- Биллинг: `POST /api/v1/subscriptions`, `GET /api/v1/subscriptions/me`, `POST /api/v1/subscriptions/cancel`, webhook-эндпоинт для платёжного провайдера (ЮKassa/CloudPayments и т.п.) — ничего из этого не существует, ожидаемо для домонетизационного MVP.
- Админ/контент-эндпоинты — сейчас банк заданий тренажёра наполняется только через `python -m app.seed_tasks` (статический Python-скрипт, не API) — для Stage 2 понадобится хотя бы минимальный защищённый CRUD для контента (или отдельная админка).
- Единый формат ошибок (`{"error": {"code": ..., "message": ..., "request_id": ...}}`) вместо разнородного `detail`.
- Пагинация для списковых эндпоинтов (`limit`/`cursor`).
- `Idempotency-Key` хотя бы для `POST /trainer/submit` и `POST /assistant/chat`.
