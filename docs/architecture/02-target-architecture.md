# Целевая архитектура — 3 стадии (Фаза 14)

> Принцип по всем стадиям: **не вводить сложность заранее** — переход на следующую стадию обоснован конкретным триггером, а не календарной датой или амбицией.

## Стадия 1 — текущий MVP, ~100 пользователей (0–6 мес.)

Практически без изменений относительно того, что уже есть — это правильный масштаб для монолита.

- **Frontend**: Next.js как есть. Единственное обязательное добавление — health-check ошибок авторизации (глобальный interceptor на 401 → редирект на `/login` + попытка `refresh_token`, которая сейчас не реализована вовсе).
- **Backend**: FastAPI-монолит как есть, добавить: реальный `X-Forwarded-For`-парсинг для rate limit за прокси (см. `security-audit.md`), базовое событийное логирование (см. `analytics-spec.md`), отключение `/docs` `/openapi.json` в проде либо их защиту Basic Auth.
- **БД**: PostgreSQL как есть, добавить таблицы `events` (для аналитики, см. Стадия 1 в `analytics-spec.md`) и нормализованный `topics`/`skills` справочник (см. `database-design-v2.md`) — это дешёвое изменение уже сейчас, которое снимает архитектурный долг до того, как на строковые совпадения тем завяжется больше логики.
- **AI**: продолжать интеграцию по существующему HTTP-контракту (`ai-service-contract.md`) — он спроектирован правильно, менять не нужно. Приоритет — définir реальный формат ответа от сервиса Валентины и синхронный vs асинхронный паттерн (см. `ai-tutor.md`, открытый вопрос по латентности).
- **Инфраструктура**: тот же `docker-compose` на одной VM. Добавить: CI (GitHub Actions — lint+typecheck+test на каждый PR, это отсутствует полностью и уже стоило нескольких `Revert`-коммитов в проде), автоматический бэкап Postgres (сейчас не описан нигде).
- **Триггер перехода на Стадию 2**: устойчивые 100+ активных пользователей И первая подтверждённая платящая когорта (см. `business-model-v2.md`) — то есть гипотеза "готовы платить" подтверждена, а не просто "MVP работает".

## Стадия 2 — коммерческий запуск, ~1 000–10 000 пользователей

- **Frontend**: без смены фреймворка. Добавить SSR/ISR там, где появится публичный контент (лендинг, блог/SEO-контент для органики — сейчас такого контента нет вообще, см. `gtm-strategy.md`). Мониторинг ошибок клиента (Sentry).
- **Backend**: монолит остаётся монолитом — 10 000 пользователей не требуют микросервисов при разумном API. Добавить: горизонтальное масштабирование backend (2+ реплики за балансировщиком — тут важно, чтобы миграции из `entrypoint.sh` не гонялись на каждом старте каждой реплики, а выполнялись отдельным деплой-шагом), очередь задач (Celery/RQ или встроенный FastAPI `BackgroundTasks` с Redis) для email и потенциально асинхронного вызова ИИ-сервиса, если его латентность останется высокой (см. открытый вопрос в `ai-service-contract.md` про 38.4 сек на CPU).
- **БД**: тот же Postgres, добавить read-реплику при заметной read-нагрузке от дашборда/аналитики; ввести партиционирование `task_attempts`/`chat_messages` по времени, если объём станет заметным (не раньше, чем реально понадобится — не превентивно).
- **AI/RAG**: здесь наконец нужен реальный векторный поиск — `pgvector` в уже используемом образе Postgres достаточен для этого объёма (не нужен отдельный Pinecone/Weaviate/Qdrant при 10 000 пользователей — держит принцип "не превентивно").
- **Платежи**: подключить платёжного провайдера (ЮKassa/CloudPayments — российский рынок), таблицы `subscriptions`/`payments` (см. `database-design-v2.md`).
- **Наблюдаемость**: структурированные логи (JSON) + базовые метрики (Prometheus/Grafana или облачный аналог), алертинг на 5xx/латентность ИИ-эндпоинтов.
- **Триггер перехода на Стадию 3**: устойчивый рост >10 000 MAU, доказанная unit-экономика (LTV>CAC, см. `financial-model-v2.md`), очередь на B2B-продажи школам (что требует multi-tenant аспектов — RBAC для ролей "учитель"/"завуч", которых сейчас нет вообще).

## Стадия 3 — масштаб, 10 000 → 100 000 → 500 000+

- **Frontend**: без принципиальных изменений архитектуры, усилить CDN/edge-кэширование статических ресурсов.
- **Backend**: рассмотреть выделение ИИ-прокси/оркестрации в отдельный сервис **только если** нагрузка на LLM-инференс явно доминирует и требует независимого масштабирования от остального API (это единственный оправданный повод для выделения сервиса на этом масштабе — не "микросервисы ради модности"). Остальной монолит может оставаться монолитом значительно дольше, чем принято думать — большинство EdTech-платформ такого профиля (CRUD + AI-прокси) не требуют распада на 10 сервисов даже на 500k пользователей.
- **БД**: шардирование/партиционирование по необходимости, отдельное хранилище для событийной аналитики (ClickHouse или аналог) вместо перегрузки OLTP-Postgres аналитическими запросами.
- **AI/RAG**: возможен переход на управляемый векторный движок, если объём базы знаний/эмбеддингов перерастёт комфортный размер pgvector — но это **триггер по объёму данных, а не по числу пользователей**.
- **B2B**: полноценный multi-tenant слой (школа → классы → учителя → ученики), RBAC поверх текущей плоской модели пользователей.
- **Инфраструктура**: multi-region при реальном геораспределении пользовательской базы (не раньше).

## Явные scaling-триггеры (сводно)

| Триггер | Действие |
|---|---|
| Первая платящая когорта подтверждена | Начать Стадию 2 (платежи, CI, реплики) |
| Латентность backend p95 > 500 мс при нормальной нагрузке ИЛИ CPU одной реплики стабильно >70% | Горизонтальное масштабирование backend |
| Реальный ИИ-сервис даёт латентность ответа > 5–10 сек синхронно | Переход `assistant/chat` на асинхронный паттерн (job + поллинг/WebSocket), как уже предусмотрено открытым вопросом в `ai-service-contract.md` |
| База знаний для RAG превышает то, что комфортно обслуживает pgvector на текущей инстанции (ориентир — по факту нагрузочного теста, не заранее) | Рассмотреть выделенный векторный движок |
| Заключён первый B2B-контракт со школой | Ввести multi-tenant/RBAC-слой |
| MAU стабильно > 10 000 | Начать проектирование Стадии 3 (партиционирование, отдельная аналитическая БД) |

Ни один из этих триггеров сегодня не достигнут — по состоянию на дату аудита продукт полностью находится в рамках Стадии 1, и это корректно для его текущего размера.
