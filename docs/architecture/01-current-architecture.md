# Архитектура — текущее состояние (Фаза 13)

## Схема

```
                         ┌─────────────────────┐
   Браузер ученика  ───▶ │  Next.js frontend    │  (Docker: node:20-slim, SSR-шелл + client components)
                         │  JWT в localStorage   │
                         └──────────┬───────────┘
                                    │ HTTPS, fetch + Bearer-токен
                                    ▼
                         ┌─────────────────────┐
                         │  FastAPI backend     │  (Docker: python:3.12-slim, uvicorn)
                         │  auth/dashboard/      │
                         │  diagnostics/trainer/ │
                         │  assistant            │
                         └───┬─────────────┬────┘
                     asyncpg │             │ redis (rate limit, pwd-reset токены)
                             ▼             ▼
                   ┌─────────────────┐  ┌────────┐
                   │ PostgreSQL 16    │  │ Redis 7 │
                   │ (образ pgvector, │  └────────┘
                   │  расширение не   │
                   │  используется)   │
                   └─────────────────┘

                         (опционально, httpx, по контракту)
                         ┌─────────────────────┐
   backend ── HTTP ────▶ │  AI-сервис Валентины  │   ❌ НЕ СУЩЕСТВУЕТ как задеплоенный сервис.
                         │  (RAG + CAT/IRT)      │      AI_SERVICE_MOCK=true → вызов не происходит,
                         └─────────────────────┘      backend отдаёт статичные mock-данные локально
```

## Frontend

Next.js 14 (App Router), полностью клиентский рендеринг данных («use client» на каждой странице) — сервер отдаёт статическую HTML-обвязку, а данные (пользователь, дашборд, задания) подгружаются `fetch`-ом из браузера после гидратации. SSR/RSC фактически не используется для данных — это архитектурно нормально для SPA-подобного MVP с приватными данными за авторизацией, но означает отсутствие SEO для приватных страниц (что и не нужно — публичных страниц с контентом нет вообще).

Состояние авторизации — React Context (`AuthContext`), токен — в `localStorage`. Единая точка HTTP-вызовов — `lib/api.ts` (обёртка над `fetch`, подставляет `Authorization: Bearer`, единообразно парсит ошибки FastAPI `{"detail": ...}`).

## Backend

FastAPI, слоистая структура `api/ → schemas/ (Pydantic) → models/ (SQLAlchemy ORM) → db/session.py`. Роутеры независимы друг от друга, общая точка — `get_current_user` (JWT-зависимость) из `auth.py`, импортируемая остальными роутерами напрямую (нормально для монолита такого размера, в микросервисной архитектуре потребовало бы отдельного auth-сервиса — сейчас это не нужно).

Все операции с БД — асинхронные (`asyncpg` + SQLAlchemy 2.0 async ORM), без синхронного fallback — согласовано по всему стеку.

**AI-интеграция** — единственная точка связи с внешним миром для «умной» части продукта: `app/core/ai_client.py`, три функции (`get_next_item`, `finalize_session`, `get_chat_answer`), каждая — либо возвращает mock, либо делает `httpx`-запрос к `AI_SERVICE_URL` по контракту `docs/ai-service-contract.md`. Архитектурно это **правильное решение** — backend не завязан на конкретную ML-реализацию, контракт стабилен, ИИ-часть можно подключить без изменения схемы БД и эндпоинтов. Это единственное место в системе, спроектированное с заделом на будущее расширение, и оно сделано аккуратно.

## База данных

8 таблиц, все с суррогатным UUID PK, разумные внешние ключи и индексы на FK-колонках (см. `03-database-design-v2.md` для полного разбора). Нет ни одной вспомогательной ML/аналитической таблицы (эмбеддинги, события, лог обращений к ИИ) — вся систем-аналитика сейчас отсутствует.

## Инфраструктура и деплой

`docker-compose.yml`: 4 сервиса (`db`, `redis`, `backend`, `frontend`), volume для Postgres, healthcheck только у `db`. `entrypoint.sh` бэкенда сам гоняет `alembic upgrade head` и сид тестовых заданий при каждом старте контейнера — удобно для MVP (не нужен отдельный CI/CD-шаг), но **опасно при масштабировании на несколько backend-реплик** — каждая реплика при рестарте попытается применить миграции параллельно (Alembic обычно справляется благодаря блокировкам транзакций, но это не рассчитанный сценарий, стоит явно продумать при переходе к Stage 2).

Прод — за реверс-прокси RelaxDev (`axiom-mvp.relaxdev.ru` → frontend, `axiombackend.relaxdev.ru` → backend, порт бэкенда явно перебинден на 8080 под ожидания прокси, см. коммит `47ef249`). CI/CD как таковой не обнаружен (нет `.github/workflows`, нет иных пайплайнов в репозитории) — деплой, судя по серии `Revert`-коммитов, делается вручную/полу-вручную.

## Наблюдаемость (observability)

Логирование — только `logging.basicConfig` со стандартным форматтером, вывод в stdout контейнера. Нет структурированных логов, нет трассировки запросов, нет метрик (Prometheus/OpenTelemetry отсутствуют), нет алертинга, нет health-дашборда кроме примитивного `GET /health`. Для 100 пользователей это допустимо; для коммерческого запуска — недостаточно (см. `02-target-architecture.md`).

## Безопасность на уровне архитектуры

CORS ограничен одним доменом (хорошо). JWT с алгоритмом HS256 и секретом из `.env` (стандартно для монолита с одним издателем токенов). Пароли — bcrypt. Rate limiting — Redis fixed-window, с известным нерешённым риском реального клиентского IP за прокси (см. `03-live-vs-code.md`, `docs/security/security-audit.md`).

**Исправление (ранее в этом документе ошибочно утверждалось обратное — не было проверено, а не должно было приниматься на веру):** `.env` **закоммичен в git** — в репозитории вообще нет `.gitignore` (`git ls-files | grep .env` подтверждает файл в индексе, история — минимум 3 коммита). Значения в закоммиченном `.env` сейчас совпадают с плейсхолдерами из `.env.example` (`JWT_SECRET=change-me-to-a-random-64-char-string`), то есть реального секрета в самом репозитории не лежит — но поскольку `docker-compose.yml` грузит backend именно из этого `.env` (`env_file: .env`), и `03-live-vs-code.md` подтверждает, что прод разворачивается из этого репозитория 1:1, критично проверить вручную, не использует ли прод этот же дефолтный `JWT_SECRET` — если да, любой может подделать валидный JWT для любого пользователя. Также `docker-compose.yml` публикует порты Postgres (`5432`) и Redis (`6379`) наружу с дефолтными учётными данными `axiom`/`axiom` и Redis без пароля вовсе. Оба пункта — **CRITICAL**, подробный разбор и план исправления в `docs/security/security-audit.md`.

## Итоговая оценка архитектуры MVP

Для заявленного масштаба (~100 пользователей, валидация гипотезы) архитектура **соразмерна задаче** — это ровно то, что рекомендует `CLAUDE.md` («не строить микросервисы без причины», «предпочитать наименьшую реализацию, которая валидирует гипотезу»). Монолит + Postgres + Redis + чёткий HTTP-контракт для ИИ-части — разумный выбор. Главный архитектурный риск сейчас не в том, как построен код, а в том, что **вокруг несуществующего ИИ-сервиса построена вся ценностная гипотеза продукта**, и текущая архитектура (справедливо) не может это компенсировать — только предоставляет чистую точку интеграции, когда сервис появится.
